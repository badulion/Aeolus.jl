The Berlin case

The Berlin (Alexanderplatz) run is the flagship example of Aeolus. Until 2026-10-06 every physics module in src/ had to be exercised by it (the rule of #123); the maintainer dropped that rule, and the example has no test suite of its own (#320): the physics it couples is tested in the module tests, and its end-to-end runs are test/urban_checks.jl (smoke runs) and validation/urban_checks.jl (flagship and parent runs). Since #126 it is not a script but a small framework, built so that many couplings can be added independently and at the same time; since EX-a (#438) that framework is part of the package; since ONE-e (#454) it is the urban site of the model (a model config with [urban] enabled and one section per urban component, see Urban site), stepped through the core's stage pipeline; since ONE-k (#474) it is Aeolus.Urban in src/components/urban.jl and src/components/urban/, the site a component of its domain (UrbanSite), stepped by step!(model) and run by the model's run loop. The Berlin case is configuration only: examples/urban/berlin_*.toml, its static drivers (OpenStreetMap buildings, the parent's land use) and its dynamic driver (the Lindenberg sounding).

julia --project -m Aeolus run examples/urban/berlin_summer.toml --set time.nsteps=1800   # 1 h at dt = 2 s

From Julia (the tests do this):

using Aeolus
const UC = Aeolus.Urban

cfg  = UC.site_options(load_run_config("examples/urban/berlin_summer.toml"; overrides = ["time.nsteps=1800"]))
site = UC.build_case(cfg)                            # the UrbanSite, the first component of site.model's domain
print(UC.describe(site))                             # couplings and schedule
Aeolus.Components.run_to!(site.model, cfg.nsteps * cfg.dt)   # log events (frames, timing, ledgers); no NetCDF

What the case prints is the installed logger's choice (#347; there is no verbose setting and no io keyword): every line is a structured log record with subsystem = :urban (:berlin before #438), an event key and its values as key-values (#338; the code is src/components/urban/site/diagnostics.jl):

eventlevelkey-values

:run_startInfonsteps, t_end, dt, variable_dt, records
:frameInfoeach output record: frame, wall and the frame diagnostics (hour, solar_elevation, Ts_min/Ts_max, sw_min/sw_max, theta1_min/theta1_max, qv1_min, dew_max, ql1_max)
:couplingInfowith each frame, one per coupling that declares diagnostics: coupling and its values
:run_endInfosteps, wall, records (frames), peak_uhi, max_div

:ledgerInfoledger = :surface per class (Rn, H, LE, G, dS, residual, the extra terms, closure, W m⁻²); :water (storage, the sources, residual, kg m⁻²); :heat per layer (storage, closure, W m⁻²); :heat_term per attributed term (W m⁻² per layer)

with_logger(NullLogger()) do … end silences a run. Under aeolus run (below) the run folder's log takes everything from [logging] file_level (debug) up and the console [logging] console_level (info; debug adds the setup summary).

Diagnostics

A coupling reports through the library's diagnostics registry (Logging): it declares its scalars with diagnostics(c, case) and its vertical profiles with profile_diagnostics(c, case), as it declares output_fields. The same declarations are the coupling's :coupling log event and its columns of the run folder's diagnostics.csv and diagnostics.nc, so there is one source of truth for what a coupling reports. case_diagnostics(case) collects every scalar of the run:

  • the dynamical core's (ke_mean, max_div, theta_min, …);
  • the frame quantities (Ts_min, sw_max, …), the closure the steps run under sgs. (sgs.nu_h_max, sgs.e_mean, …);
  • the ledgers under ledger.: ledger.surface.<class>.<term> (Rn, H, LE, G, dS, closure, W m⁻², mean over the run, for every class present and domain), ledger.water.storage / ledger.water.residual (kg m⁻²), ledger.heat.storage / ledger.heat.closure (W m⁻², whole column);
  • the stage timing, wall.<stage>.<entry> (s, cumulative);
  • each coupling's, prefixed with its name (pressure_multigrid.cycles, timestep_adaptive.dt_mean, nesting.boundary_heat_top, …).

Every wall-clock quantity is named wall.…: a coupling declares one as wall.<x> and it is filed as wall.<coupling>.<x>, so a comparison of two runs that must agree bit for bit (the configuration round trip of #358) drops them all by the prefix, with the CSV's own wall column. The rows carry the step's dt, what limited it (dt_limiter: the binding CFL limit, dt_min, dt_max, growth, or the coupling whose limit_dt shortened it) and its retries. The quantities that cost a reduction or more are on the costly cadence ([logging] diagnostics_cadence, 60 s simulated); counts and solver residuals every step. The three that cost more than a step (the SGS a-priori metrics, the Leighton ratio, the transition summary and its profiles) are evaluated once per output record (per_record), as their report lines were, and repeated in the rows in between. Measured on the 64 × 64 × 64 summer case (#338): a step 122 ms; every diagnostic and profile evaluated afresh 193 ms, of which those three 168 ms; with them once per record a costly row costs 16 ms, 0.4 % of the run at a 2 s step and the 60 s cadence.

The flagship is configured in TOML (CFG-c, #358): the scenarios are the shipped files examples/urban/berlin_<scenario>.toml, model configs of an urban site (ONE-e, #454),

julia --project -m Aeolus run examples/urban/berlin_summer.toml --set time.nsteps=1800 --set output.cadence=600

with no wrapper script (#438). The run folder (runs/<date>_<name>_<id>/) holds run.toml, the log, diagnostics.csv and output/results.toml (the run's own checks: the ledgers' closure, the timing); the NetCDF output (the variables of [output] variables) still goes to examples/urban/output/alexanderplatz.nc ([output] path and netcdf). See the urban site for the schema; site_options(load_run_config(path)) in Julia reads the same file.

Configuring with TOML

A variant of a scenario is a complete copy of its file with the keys that differ changed (there is no extends: every config is self-contained, ONE-b #451), or a --set on the command line:

# my_berlin.toml: a copy of berlin_summer.toml, with
[run]
name = "summer_no_traffic_nox"

[sgs]                              # a slot: its selector names the provider (ONE-m, #476)
model = "smagorinsky"              # the section holds this provider's options only
stress = "symmetric"

[chemistry]
scheme = "aq_chem"
nox_street = 0.0                   # a provider option, of its default_options' form

[pollutant]                        # an additive component: on or off
enabled = true

julia --project -m Aeolus check my_berlin.toml validates it, resolve prints every option it resolves to, and run starts it. In Julia, site_options(load_run_config("my_berlin.toml")) gives the site's options that build_case takes. Every key, with its type, default, units and range, is in the generated option reference of the model; the guide to files, overrides, replays and --resume is Run configuration. The run's run.toml holds the resolved config, so aeolus run <folder>/run.toml replays the run bit for bit.

A coupling's default_options is its section. The model's section [<name>] of an additive urban component (coupling_section) is generated from its default_options NamedTuple: enabled (default false: every additive component is off until its section enables it), then one option per key (coupling_options!); a provider of an urban slot is a block of the slot's section instead (urban_slot_section, ONE-m #476: [sgs] model = "smagorinsky" and the smagorinsky options), its options generated the same way: its TOML key ASCII snake case (option_key: U_g → u_g, τ → tau), typed by its default's form (a Symbol is a string, a tuple an array of its length, a NamedTuple or a table by surface class a sub-table), with its units (OPTION_UNITS); the meaning of each key is documented on the coupling's docstring. Adding a key to default_options is all it takes to make it configurable from TOML and listed in the option reference; there is no separate schema to edit. Every urban slot (:sgs, :surface_exchange, :core, …) has exactly one provider, the one its section's selector names (URBAN_SLOT_SECTIONS; default: the URBAN_DEFAULTS one), and the section holds that provider's options only (an option of another provider is a config error naming the providers that have it); the site's own options — the ground's anchor, the clock, the periods of the radiation and the soil, the core's Coriolis parameter, Smagorinsky coefficient and sponge, the lateral boundaries and the initial state — are [urban]; the grid, ν, θ₀, g, dt and nsteps are the model's [grid], [dynamics] and [time], and the drivers the domain's static_driver and dynamic_driver.

The component interface

An urban component is a struct <: UrbanComponent (an Aeolus.Components.AbstractComponent) plus the methods below for its type. Only component_name and the run_stage! methods of the declared stages are required; everything else has a default. Its name, slot and incompatibilities are the component interface's (Components.component_name, slot, incompatible); the rest take the case, since the components read its shared state (the ground, the surface bus, the tracers, the reference state).

methodmeaning
component_name(::Type{C})unique Symbol: its section [<name>], its key in cfg.components
slot(::Type{C})nothing (additive, on/off) or an urban slot (URBAN_SLOTS) such as :microphysics: a site enables exactly one component per slot
provider(::Type{C})its short name within the slot (:kessler), for messages and the smoke runs' labels
modules_used(::Type{C})Aeolus submodules it runs
default_options(::Type{C})NamedTuple: the TOML schema of its section [<name>] (closed keys, each value of its default's form); the section's values on top of it are cfg.components[name], passed to build
incompatible(::Type{C})the component types it cannot run with
stages(::Type{C})((stage, order, Cadence), …), at most one entry per stage, the stages the pipeline's (Components.PIPELINE); a Symbol period is one of cfg.cadence (:radiation, :soil, :surface: [urban] radiation_period, …; :output: [output] cadence)
build(::Type{C}, case, opts)construct the instance (default C())
init!(c, case)after every component is built, by init_priority, then in URBAN_COMPONENTS order
run_stage!(c, case, ::Val{S}, dt)the work of stage S
output_fields(c, case)OutputFields added to the NetCDF file
budget!(c, case, ledger)this step's surface-energy and water terms (see the ledger)
diagnostics(c, case)Vector{Diagnostic}: the scalars it reports, in diagnostics.csv / .nc and its :coupling log event with each output record (see Diagnostics)
profile_diagnostics(c, case)Vector{ProfileDiagnostic}: its vertical profiles, in diagnostics.nc
smoke_variants(::Type{C})extra smoke-run configurations, a tuple of NamedTuples (see the smoke runs)
smoke_check(c, case)Vector{Pair{String,Bool}} of physics checks on the state after a smoke run (test/urban_checks.jl)
sim_options(::Type{C}, cfg, mesh, opts)keywords of the dynamical core's constructor (the solver of BoussinesqSimulation; tol, maxit of a sound-proof core), before the core is built (see numerics slots)
step_options(c, case)keywords added to every dynamics step, step! or step_imex! (e.g. momentum_advection, sgs)
incompatible_reason(::Type{C})why the incompatible pairs fail, appended to the selection error

Two slots drive the dynamics itself and have four more methods (#133, see Dynamical core and time integration):

methodmeaning
build_core(::Type{C}, cfg, mesh, ref, simkw)slot :core: construct the dynamical-core simulation (case.sim) on the case's reference state ref with the merged sim_options keywords simkw; a keyword it does not take is an error
next_dt(c, case)slot :timestepper: the length of the next step (default cfg.dt)
advance_dynamics!(c, case, dt)slot :timestepper: advance case.sim by dt with the composed :body_force / :post_predictor hooks and the numerics slots' case.step_kwargs (default dynamics_step!: one step!)
variable_dt(::Type{C})slot :timestepper: true if next_dt varies; the run then goes to the simulated time nsteps · cfg.dt, its last step landing on it
stable_dt(c, case)slot :timestepper, variable_dt providers: the longest step the provider's stability limits (CFL, diffusion, buoyancy, Coriolis) and dt_max allow from the current flow, without the growth limit and without side effects (default Inf). step!(model, dt) throws an ArgumentError for a dt above it, before any stage runs (#392; check_step_dt)

A keyword from sim_options or step_options is never dropped: every time stepper passes case.step_kwargs to the step it takes, and a core or stepper that cannot take a component's keyword declares that component incompatible (with incompatible_reason), so the configuration fails with the reason instead.

The config checks of an urban site (urban_checks, run when a config is loaded) report a declared incompatibility between two selected components (naming their sections, [core] model = "anelastic" is incompatible with [pressure] solver = "cosine_fft") and an option of the wrong form; an unknown option or section, a selector naming no provider and an option of another provider are the schema's errors.

Cadences are in seconds. Cadence(600.0) fires on the step that crosses a multiple of 600 s, floor(t_new/P) > floor(t_old/P); Cadence(:radiation; first = true) names a period in cfg.cadence and also fires on step 1. With dt = 2 s this is exactly the old n % 300 == 0 || n == 1 over a whole day. With an adaptive dt the entry still fires once per period crossed, and the adaptive stepper caps dt at the shortest cfg.cadence period so that no firing is skipped. The surface exchange steps its surfaces (the soil columns of ground_soil included) forward by its period P and gives the held fluxes to the air; a step that runs past the end of a surface interval delivers them only up to that end and carries the rest of the step into the next interval (air_delivery_time!), so the air receives every interval's fluxes for exactly P (smoke check, 1e-9 P; with a fixed dt dividing P that is every step's dt, bit for bit). buildings_citymean advances its zone over the next radiation interval, which it cannot know under an adaptive dt; it uses the nominal P, so the zone and the air it heats disagree by less than one step per interval (≤ 10 s of 600 s) and the difference does not accumulate. Every budget! books with ledger.dt, the current step's length, never cfg.dt.

The stage loop

One step of the case is one step of its Domain through the core's stage pipeline (Aeolus.Components, ONE-a #450; since ONE-e #454), step!(model) (ONE-k, #474): the site itself (UrbanSite, the domain's first component: the step count, the local hour and the budgets' start-of-step snapshot in :clock, the captures of the fixed-gradient top and the open faces in :tendencies, the sanity check in :budgets, the frame's log events in :output; it takes the core step with its :timestepper component) and one component per enabled coupling (UrbanEntry), each with the pipeline stages, cadences and places in a stage (Stage(…; order)) its coupling declares. Within a stage the entries run in that order:

:clockthe step count, the local hour, the budgets' snapshot (UrbanSite, first)
:nest_syncnesting (10): opens a parent window when the child has reached the last one — the parent takes its step, the child's nest faces point at the new window (see Nesting)
:radiation (600 s, and step 1)column_radiation (5), radiosity_sun (10), cloud_shadow (15), buildings_citymean (20)
:sw_modifierssw_modifiers (10, tree shade)
:surface_fluxsurface_exchange (10): the held H, E into the first air cell (step 1: the first surface step)
:sourcesbuildings_citymean (10), traffic_heat (20), glass (30)
:chemistryaq_chem (10)
:transportscalar_advection (10)
:microphysicsmicro_kessler (10), fog_dew (20)
:tracerspollutant (10)
the core: advance_dynamics! of the :timestepper provider (default one step!) with :tendencies, :body_force and :post_predictor called from its hooks:tendencies: the top and open-face captures (UrbanSite); :body_force: nesting (5: the two-way θ booking, a no-op one-way, #267), geostrophic (10), moist_buoyancy (20), wall_model_facades stencil-flux removal (40); :post_predictor: ibm (10), wall_model_facades facade stress (12), surface_exchange drag (15), veg_drag (20); the step_options of the numerics slots
:surface_updatesurface_exchange (10: collects bus.sensible; every surface period steps all surfaces, soil included), aq_chem ra / vd refresh (90, every 30 s)
:column_tendencycolumn_radiation (10)
:nest_feedbacknesting (10): closes the window when the child reaches its end (one-way: clock and statistics; mode = :two_way, #267: also the feedback onto the parent, see Nesting)
:budgetsthe site's finiteness check (a blowup throws), then the budgets close: every coupling's budget!, and the change of water in the air (UrbanSite)
:output (1800 s)the frame's log events (the site), then turbulence_diag (10); the NetCDF record is the run's writer's, after the step

The order is that of the urban stage loop the pipeline replaced (ONE-e, #454: the 54 runs of the smoke matrix reproduce its state bit for bit), which was the order of the pre-refactor loop, floating-point order included (#126). Three of the loop's stages are the pipeline's under its names (:nest_parent is :nest_sync, :anthropogenic :sources), its :fog_dew stage runs as the second entry of :microphysics (between it and its old place only the passive pollutant ran, which reads none of what fog and dew change), and :transport is a stage of the pipeline. Every entry is an attribution context of the air-heat budget (the domain's budgets; the dynamics' in-core entries are measured on θ's tendency).

The order was the order of the pre-refactor loop, floating-point order included (#126). The surface exchange (#129) replaced the slab, whose latent flux sat at the end of :anthropogenic (now :sources) and whose Ts clamp ran in :sanity only to keep that order; see Surface exchange.

The site logs the wall time of every entry at the run's end (the :timing events and the wall.* diagnostics). At #126, in the 1 h flagship run (1800 steps, first-call compilation included), the largest entry was the WENO-Z5 scalar transport, about 17 ms/step, ahead of step! itself (about 12.5 ms/step), then fog_dew (6.1), radiosity_sun (5.5 averaged over all steps) and soil_urban (2.8); everything else was below 1 ms/step (table in the #126 PR). Since then soil_urban has been replaced by the surface exchange (#129; its surface step costs 13.6–16.3 ms per step of the adaptive stepper, remeasured on master 915bd49) and the chemistry (#135) adds five advected species; see the cost paragraphs of those sections.

The serial baseline before threading (#295, KA-c) removed the runtime integer power from the WENO-Z / TENO weights, the plane copies from every halo fill and the per-level slice copies from the dew, with no change to any bit of the smoke matrix or of 12 flagship steps. Shared state

Couplings never keep a private copy of a quantity another coupling needs.

  • SurfaceBus (case.bus, per column): Ts, sw, lw, the extra surface loss sensible (energy other couplings take from or give to the surfaces this step — window sun, glazing transmission, dew heat; not the turbulent sensible flux), the dew reservoir dew, the clear-sky beam sw_beam, the per-class params, the last radiosity solutions swsol/lwsol, the sky longwave L_sky and the direct/diffuse shortwave dni/dhi the :column_radiation slot hands the radiosity solve (#130; NaN shortwave means "Bird"), and (#129) the per-column surface (AbstractSurface), the roof-aware air level k_air, the forcing each surface last saw (T_air, q_air, U, z_ref), the fluxes it returned (Rn, H, LE, G, E, u_star) and the dew_mask.
  • Surface factories. A coupling that provides the surface of a class registers register_surface_factory!(case, class, name, (case, site) -> surface) in its build, where site::SurfaceSite carries the class, the initial skin temperature, the child column (nothing for a tile of a parent column) and an optional roughness override (take the roughness from class_roughness(case, site)). class_surface(case, site) is the one class-to-surface factory: the surface exchange builds every child column's surface with it in its init! (a SlabLand for a class nobody claims), and the parent's tiled surface (#249, below) every tile. This is how the park (#140), water (#141) and facet (#139) couplings replace a class's surface — in the child and the parent at once — without touching the surface exchange.
  • Tracers (case.tracers): ensure_tracer!(case, :qi; advect = true, positive = true, units = …, long_name = …) creates or returns a cell-centred field; flags are OR-ed, so two couplings share one ql. The :transport stage advects every tracer with advect = true in registration order, and every tracer with output = true is written to the NetCDF file. The core registers qv, ql (advected) and qr. A tracer diffuses with the closure's κt unless it names its own diffusivity (ensure_tracer!(…; diffusivity = case -> field)): the SGS TKE e of the :tke provider diffuses with 2ν_t (#182). Passive tracers (qv, ql, the chemistry species, the pollutant) never name one: they share θ's κ_t under every :sgs provider, AMD included (#234, see below).
  • Geometry (case.geom): mask, surface classes, scene, view factors. Couplings may add classes at init! (the glass coupling does). The scene is built with class_map = scene_class_map(sfc), so the ground facet of every open column has the material of its class (park, water, street; wall-tagged cells are street ground).
  • Reference state (case.ref, see below): the hydrostatic p̄, ρ̄, T̄, Π̄ per level. Every coupling that needs a pressure, converts a flux into a mixing-ratio or θ increment, or turns θ into T takes it from here (ref_pressure, ref_density, ref_exner, surface_pressure, ref_ρcp), never from a constant of its own.

Modifying bus.sw. The radiation provider writes bus.sw only at the radiation cadence; the :sw_modifiers stage runs every step. A modifier must therefore act on the unmodified field, not on its own previous output. sw_modifiers keeps that field (sw_base), takes a new one whenever bus.sw differs from what it wrote on its previous step, and rebuilds bus.sw = cloud(shade(sw_base)) each step. A second modifier added later belongs in the same pattern. Before #128 the tree shade and the cloud shadow multiplied bus.sw in place, so they compounded between radiation updates.

The case is checkpointed whole (#269): checkpoint_state(case) is the structural state of the built case (every coupling's state included, so a new coupling needs no checkpoint method of its own), restored into a fresh build by aeolus run <folder> --resume; see Checkpoint / restart.

Initial state: the Lindenberg sounding (#247)

Until #247 the case started from an analytic profile, θ = 293 K up to 100 m and +3 K/km above, with $q_v = 10\,{\rm g\,kg^{-1}}\,e^{-z/800\,{\rm m}}$ and 1013.25 hPa at the ground. #238 showed that this profile cannot cap a convective boundary layer, and the nesting parent (epic #246) must start from the same observed state as the child. The summer case now starts from the radiosondes of the Lindenberg observatory (WMO 10393, 60 km south-east of Alexanderplatz).

Case day. The epic first named 20 June 2024. That day was overcast (DWD hourly total cloud cover 7–8 oktas most hours at Lindenberg and Berlin-Tempelhof; the 12 UTC sounding is saturated at 907 hPa), so by the maintainer decision of 2026-10-05 the case moved to 29 June 2019, a clear day of the late-June 2019 heat wave: 0–2 oktas at Lindenberg and Berlin-Brandenburg from 00 UTC on the 29th to 16 UTC on the 30th, and a 12 UTC dew-point depression of at least 6 K below 700 hPa. The day is a Saturday; case_weekday(cfg) now feeds the weekday of cfg.date to the building schedules (they assumed the Thursday of 20 June 2024 before).

Data. aeolusprep fetch-sounding (AeolusPrep.jl; formerly examples/urban/data/fetch_lindenberg.jl) downloads the IGRA2 record of GMM00010393 from NOAA NCEI (public domain; Durre et al. 2018) and writes lindenberg_10393_20190629.csv: the 00/06/12/18 UTC launches of 29 June and the 00/06 UTC launches of 30 June, with pressure, reported geopotential height, T, T_d, wind and the IGRA QC flags. Its header records the URL, the download date, the station elevation (launch site 112 m, not the 97.7 m of the IGRA station list: with 97.7 m every launch misses the reported heights by 11–19 m) and the case-day check. The profiles are the GTS standard and significant levels, not the full-resolution BUFR ascent.

Profiles (src/large_scale_forcing/sounding.jl). read_sounding reads the CSV; sounding_profiles(s; z_top) returns θ, $q_v$, u, v and p as ForcingTables on heights above the launch site and the release times. Heights are hypsometric (virtual temperature from MoistThermodynamics), θ uses its Exner function and $q_v$ its $e_s(T_d)$; no thermodynamics is defined in the reader. The reported geopotential heights are used only as a check: below 3 km the computed heights match them to RMS 0.8–4.3 m per launch, within the ±4.7 m that the whole-hPa surface pressure of the GTS message allows.

The case (site/reference_state.jl). initial_θ(cfg) remains the one definition of the initial θ: forcing_value of the θ table at the case start, 06:00 CEST = 04:00 UTC, which lies between the 22:45 and 04:45 UTC releases (weight 0.875 on the later one). initial_qv(cfg) does the same for $q_v$ and replaces the inline exponential of build_case. case_surface_pressure(cfg) reduces the launch-site surface pressure from 112 m to the case's 34 m with the surface virtual temperature. build_reference integrates from it, and so does every consumer of the reference state, the nesting parent included. The heights of the sounding are used as heights above the case's ground: the profile is taken as horizontally homogeneous over 60 km and as terrain-following over the 78 m elevation difference.

Reference state and moist buoyancy

The Boussinesq core carries neither pressure nor density, and before #131 each coupling assumed its own: fog and dew an isothermal 8 km scale height from 1013.25 hPa, the surface, building and traffic fluxes and the ledger ρ = 1 (ρcp = 1005). Since #131 site/reference_state.jl builds one hydrostatic profile per case, Aeolus.Anelastic.reference_from_profile of the initial θ(z) (see the initial-state section above) from case_surface_pressure(cfg) (1018.4 hPa at the ground on the summer case day since #247; 101 325 Pa for the idealised profile), with the dry-air constants of MoistThermodynamics (so T = θ Π̄ is the temperature the fog adjustment and the saturation functions assume) and the g of the dynamics. It is exactly (1e-12 Pa m⁻¹) in the discrete balance of the anelastic core and 5e-8 from an RK4 integration of the continuous hydrostatic equation. The isothermal profile it replaces was 0.17 % off at the flagship's top level; the density is 1.20 kg m⁻³ at the ground in summer, 1.30 in winter.

Moist buoyancy (components/urban/moist_buoyancy.jl, on by default). The core adds only the dry buoyancy g (θ − θ₀)/θ₀ (sim.moisture = false: the water lives in the tracer registry). In :body_force the coupling adds the rest of the density-potential-temperature buoyancy,

g (θ_ρ − θ)′ / θ₀,     θ_ρ = θ (1 + q_v/ε − q_t) ≈ θ (1 + 0.608 q_v − q_c),

from MoistThermodynamics.density_temperature, at every interior w face (the two adjacent centres averaged, as the core does for θ); the operator is Operators.moist_buoyancy_perturbation! / add_moist_buoyancy! (moved out of the coupling in ONE-e, #454). The prime is the deviation from the mean over the fluid cells of the level: a horizontally uniform force is a pure pressure gradient in the incompressible core, so subtracting it only changes the diagnosed pressure. The condensate q_c is every tracer the ledger counts as water other than qv (ql and qr today), so a microphysics provider that calls water_tracer! has its species loaded without touching this coupling. It writes b_moist (m s⁻²) to the NetCDF file and declares diagnostics (rms and max of b′, max RH and min dew-point depression of the lowest layer).

In the flagship configuration (1 h from 06:00, no fog) it costs 0.86 ms/step. At the end of the hour the rms moist buoyancy is 8.8e-4 m s⁻² (max 1.8e-2, the buoyancy of 0.5 K), a quarter of the rms dry buoyancy perturbation (3.6e-3). In the same hour run without the coupling, the moist buoyancy the state would have is twice as large (rms 1.8e-3, max 3.4e-2): with the term on, the light, humid air the buildings and surfaces release rises and mixes instead of accumulating as anomalies. The two runs also differ in the minimum level-1 humidity (4.8 g/kg with, 3.3 without) and in dew deposition (1.6e-3 against 2.9e-3 kg m⁻²), but after an hour of turbulence part of that is the divergence of two chaotic runs, not the term alone.

Adding a coupling

This is the whole procedure. It touches one new file and the PR body; no shared file of the case is edited.

1. Put the physics in src/. A coupling only wires a src implementation into the 3-D run. If the physics is missing, add it to the right src module with its own tests first. Never copy it into the example.

2. Write src/components/urban/<name>.jl. One struct and the interface methods it needs; then add the type to URBAN_COMPONENTS (src/Urban.jl):

# P3 microphysics (Aeolus.P3Microphysics) in the :microphysics slot.

struct MicroP3{W} <: UrbanComponent
    work::W
end

component_name(::Type{<:MicroP3}) = :micro_p3            # unique; its section [micro_p3]
slot(::Type{<:MicroP3})          = :microphysics         # or nothing (additive)
provider(::Type{<:MicroP3})      = :p3                   # its short name in the slot
modules_used(::Type{<:MicroP3})  = (:P3Microphysics,)    # the Aeolus modules it runs
default_options(::Type{<:MicroP3}) = (skip_dry = true,)
stages(::Type{<:MicroP3}) = ((:microphysics, 10, EVERY_STEP),)

function build(::Type{<:MicroP3}, case, o)
    ensure_tracer!(case, :qi; advect = true, positive = true, units = "kg kg-1",
                   long_name = "ice mass")               # transport picks it up
    return MicroP3(...)
end
init!(c::MicroP3, case) = water_tracer!(case.budgets, :qi) # count it as water

function run_stage!(c::MicroP3, case, ::Val{:microphysics}, dt)
    ...                                                  # calls into Aeolus.P3Microphysics
end

budget!(c::MicroP3, case, l) = add_water!(l, :precipitation, -c.surface_precip_step)

smoke_check(c::MicroP3, case) =
    ["ice ≥ 0" => minimum(interior_view(tracer(case, :qi))) >= 0,
     "precipitation ≥ 0" => c.surface_precip_step >= 0]

The file is picked up by the directory scan (include order: the sorted file name); build_case builds the enabled components in the order of URBAN_COMPONENTS, and within a stage the case's domain runs them by their declared order, then by name.

  • Off until a config enables it. An additive component's section has enabled = false by default: a config runs it only when it says [micro_p3] enabled = true. A component of an urban slot is a provider of the slot's section instead (URBAN_SLOT_SECTIONS, ONE-m #476): a config selects it with [microphysics] scheme = "p3", and the section then holds its options; the slot's default provider is the one of URBAN_DEFAULTS. URBAN_DEFAULTS is the reference selection (what default_run_config() enables and the smoke runs vary). Coupling new physics into the example is welcome where it makes sense, not required (the rule of #123 was dropped on 2026-10-06); quote the cost per step from the :timing events in the PR.
  • Cadence. An expensive stage can run every P seconds: Cadence(600.0), or Cadence(:mykey) with a default in cfg.cadence (add the key through the scenario or your option; a missing key is an error). Stages inside step! (:body_force, :post_predictor) must run every step.
  • Shared state goes through the bus, the tracer registry and the geometry, never a private copy (see above). If you need a bus field that does not exist, add it to site/bus.jl additively and say so in the PR.
  • Replacing a coupling. Delete the old file (the issue says which) and move its budget! terms and checks over. The ledger closure of the smoke runs fails if a term that changes a surface temperature or the water in the air is lost.

3. Report to the ledger. If the coupling changes a surface temperature, adds or removes water from the air, or clips anything, book it in budget! (next section). The smoke runs of test/urban_checks.jl assert the closure, and every run reports it in its output/results.toml, so a missing term shows.

4. Give it smoke coverage. The smoke runs already run every additive coupling and one configuration per non-default provider, so most couplings need no smoke_variants. Add one for a configuration that is not reached that way, for example an option that changes the code path:

smoke_variants(::Type{<:MicroP3}) =
    ((label = "sgs cloud on", physics = Dict(:microphysics => :p3),
      options = Dict(:micro_p3 => (sgs_cloud = true,))),)

Each variant is a NamedTuple: label, then physics and options (merged into the everything-on configuration), then any field of the site's options (nsteps = 30, size = …; written as the --set override of its key, SITE_FIELDS). Write smoke_checks that assert physics: a conservation or a budget, a bound that follows from the equations (a maximum principle, positivity, a range set by the thermostat), a sign that follows from the physics. "It ran" is already asserted for every coupling.

5. Run and quote. julia --project=. test/run.jl --only urban_checks.jl locally (the smoke matrix alone is about 3.5 min); the physics itself is tested in its module's tests, which every PR runs. In the PR body quote one Berlin diagnostic — a ledger term is often the natural one — the configuration it was measured in, and the cost from the :timing events.

Validation of the refactor (#126)

The refactor had to be bit-for-bit. On a 1 h run (1800 steps, two records) every NetCDF variable of the refactored case is identical (==) to the pre-refactor script, and the printed frame lines match apart from the wall-clock column.

The pre-refactor script is not reproducible run to run. Two 1 h runs of the same old script, one with a freshly measured FFTW plan and one with an imported plan, differed by up to 7.5e-9 m/s in w, 4.7e-10 m/s in v and 6.0e-8 in the pollutant (Float32 output; θ, moisture and the surface fields happened to agree). The cause is FFTW.MEASURE in the cosine-FFT pressure solver: the planner times candidate algorithms and may pick a different one in each process, with different round-off, which the flow then amplifies. With the same FFTW wisdom imported into both processes (FFTW.import_wisdom) the planner is deterministic, and old and new cases then agree exactly in every variable. Bit-for-bit comparisons of the Berlin case have to fix the FFTW plan this way.

Found during #126, fixed in #132: stale velocity halos in the scalar transport. step! corrects the interior velocity after the pressure solve but leaves the halos at the predictor values. The Berlin case advects its scalars (qv, ql with WENO-Z5, the pollutant with centred differences) at the start of the next step, on those halos, so the velocity it sees is not divergence-free across the periodic seam and the flux form stops conserving: in the :smoke window after four steps the transport stage changes the domain total of qv by −4.4e-5 and of ql by −3.5e-5 per step. With the halos refreshed (fill_halos! on u, v, w) the same stage conserves both to 1.5e-15 and 3.8e-15. The fix changes the answer, so it was not in #126; the Berlin tests recorded the leak as @test_broken and asserted the conservation with fresh halos. The scalar-advection issue (#132) owned it.

The ledger (#127) measures the same leak in water. On step 1 it is much larger: the velocity halos have never been filled when the transport first runs (set! fills only the interior), and in the :smoke window the first transport step adds 7.5e-3 kg m⁻² of water, 0.8 % of the water in the air (9.4e-1 kg m⁻²); every later step removes about 3.5e-5 kg m⁻². With the halos refreshed the same steps change the water by at most 1.3e-15 kg m⁻². Over the 1 h flagship run the transport term is −2.70e-4 kg m⁻². Fixed in #132: the scalar_advection coupling refreshes the u, v, w halos before it advects (refresh_halos = true), which also gives the pollutant, which advects later in the step, fresh halos. The water change of the transport stage is now ~1e-19 kg m⁻² per run (smoke) and +6.9e-19 kg m⁻² over the flagship hour; both @test_broken became @test, and the Berlin tests kept the mechanism tested with refresh_halos = false until they were removed (#320; the smoke runs of test/urban_checks.jl still assert the water closure of the transport).
