The Berlin case

The Berlin (Alexanderplatz) run is the flagship of Aeolus: every physics module in src/ is meant to be exercised by it (the rule of #123, in CLAUDE.md). Since #126 it is not a script but a small framework, the BerlinCase module in examples/urban/, built so that many couplings can be added independently and at the same time.

include("examples/urban/BerlinCase.jl")
using .BerlinCase

cfg  = CaseConfig(:alexanderplatz; nsteps = 1800)   # 1 h at dt = 2 s
case = build_case(cfg)
print(describe(case))                               # couplings and schedule
run_case!(case)                                     # NetCDF + log + timing table

What the case prints is the installed logger's choice (#347; there is no verbose setting and no io keyword): every line is a log record with subsystem = :berlin and an event key. The setup summary (buildings, radiosity scene, surfaces, facade wall model, city-mean building) is Debug; the run's start, each output frame with the couplings' reports, the end-of-run summary, the timing table and the ledgers are Info; a blowup is an Error. with_logger(NullLogger()) do … end silences a run. alexanderplatz_diurnal.jl runs inside with_run_log("output/alexanderplatz.log"): Info and up on the console (AEOLUS_LOG=debug adds the setup summary), everything from Debug up in the log file.

examples/urban/alexanderplatz_diurnal.jl is exactly this, reading AEOLUS_NSTEPS (default 43 200 = 24 h), AEOLUS_OUTPUT_DT (seconds between records, default 1800) and AEOLUS_SCENARIO.

The work is tracked in the milestone "Berlin — full-physics flagship" under the epic #125. On master 915bd49 (after PRs #161 and #166) 10 of its 29 issues are closed and 19 are open:

  • Wave 1, 7 of 10 merged: shade / class map (#128), surface exchange and soil (#129), column radiation and cloud shadow (#130), reference state and moist buoyancy (#131), numerics slots (#132), time integration and core options (#133, PR #161; the adaptive stepper became the default in PR #166), chemistry and deposition (#135). Open: Era I add-ons (#134), the Monte-Carlo RT diagnostic (#136), visibility and fog feedback (#137).
  • Wave 2: the GMRES facet solve (#138) is merged; the per-facet walls (#139), park land column (#140), water surfaces (#141), aerosol optics (#142) and P3 slot (#143) are open.
  • Waves 3–4 and the solver issues (#144–#153) are open.

Adding a coupling means adding one file under couplings/. No shared file is edited: the file is picked up by the directory scan, registers itself, and the registry decides from the config whether it runs.

The coupling contract

A coupling is a struct <: AbstractCoupling plus methods of the contract below for its type. Only coupling_name and the run_stage! methods of the declared stages are required; everything else has a default.

methodmeaning
coupling_name(::Type{C})unique Symbol; key in cfg.physics / cfg.options
slot(::Type{C}):addon (additive, on/off) or an exclusive slot such as :microphysics
provider(::Type{C})the value of cfg.physics[slot] that selects C
is_default(::Type{C})default provider of its slot; for an addon, on by default
modules_used(::Type{C})Aeolus submodules it runs
default_options(::Type{C})NamedTuple, merged with cfg.options[name] and passed to build
incompatible(::Type{C})slot => provider pairs or coupling names it cannot run with
stages(::Type{C})((stage, order, Cadence), …), at most one entry per stage
build(::Type{C}, case, opts)construct the instance (default C())
init!(c, case)after every coupling is built, in registry order
run_stage!(c, case, ::Val{S}, dt)the work of stage S
output_fields(c, case)OutputFields added to the NetCDF file
budget!(c, case, ledger)this step's surface-energy and water terms (see the ledger)
report(c, case)an extra log line with each output record
smoke_variants(::Type{C})extra smoke-test configurations, a tuple of NamedTuples (see the smoke test)
smoke_check(c, case)Vector{Pair{String,Bool}} of physics checks on the state after a smoke run
sim_options(::Type{C}, cfg, mesh, opts)keywords of the dynamical core's constructor (the solver of BoussinesqSimulation; tol, maxit of a sound-proof core), before the core is built (see numerics slots)
step_options(c, case)keywords added to every dynamics step, step! or step_imex! (e.g. momentum_advection, sgs)
incompatible_reason(::Type{C})why the incompatible pairs fail, appended to the selection error

Two slots drive the dynamics itself and have four more methods (#133, see Dynamical core and time integration):

methodmeaning
build_core(::Type{C}, cfg, mesh, ref, simkw)slot :core: construct the dynamical-core simulation (case.sim) on the case's reference state ref with the merged sim_options keywords simkw; a keyword it does not take is an error
next_dt(c, case)slot :timestepper: the length of the next step (default cfg.dt)
advance_dynamics!(c, case, dt)slot :timestepper: advance case.sim by dt with the composed :body_force / :post_predictor hooks and the numerics slots' case.step_kwargs (default dynamics_step!: one step!)
variable_dt(::Type{C})slot :timestepper: true if next_dt varies; run_case! then runs to the simulated time nsteps · cfg.dt

A keyword from sim_options or step_options is never dropped: every time stepper passes case.step_kwargs to the step it takes, and a core or stepper that cannot take a provider's keyword declares that provider incompatible (with incompatible_reason), so the selection fails with the reason instead.

selected_couplings(cfg) checks the configuration: an unknown key, an unknown provider, an additive switch used on a slot coupling, a slot without exactly one default, and a declared incompatibility are all errors rather than silently ignored.

Cadences are in seconds. Cadence(600.0) fires on the step that crosses a multiple of 600 s, floor(t_new/P) > floor(t_old/P); Cadence(:radiation; first = true) names a period in cfg.cadence and also fires on step 1. With dt = 2 s this is exactly the old n % 300 == 0 || n == 1 (checked over a whole day in test/berlin_case.jl). With an adaptive dt the entry still fires once per period crossed, and the adaptive stepper caps dt at the shortest cfg.cadence period so that no firing is skipped. The surface exchange steps its surfaces (the soil columns of ground_soil included) forward by its period P and gives the held fluxes to the air; a step that runs past the end of a surface interval delivers them only up to that end and carries the rest of the step into the next interval (air_delivery_time!), so the air receives every interval's fluxes for exactly P (smoke check, 1e-9 P; with a fixed dt dividing P that is every step's dt, bit for bit). buildings_citymean advances its zone over the next radiation interval, which it cannot know under an adaptive dt; it uses the nominal P, so the zone and the air it heats disagree by less than one step per interval (≤ 10 s of 600 s) and the difference does not accumulate. Every budget! books with ledger.dt, the current step's length, never cfg.dt.

run_case! logs the wall time of every entry (timing_report). At #126, in the 1 h flagship run (1800 steps, first-call compilation included), the largest entry was the WENO-Z5 scalar transport, about 17 ms/step, ahead of step! itself (about 12.5 ms/step), then fog_dew (6.1), radiosity_sun (5.5 averaged over all steps) and soil_urban (2.8); everything else was below 1 ms/step (table in the #126 PR). Since then soil_urban has been replaced by the surface exchange (#129; its surface step costs 13.6–16.3 ms per step of the adaptive stepper, remeasured on master 915bd49) and the chemistry (#135) adds five advected species; see the cost paragraphs of those sections.

Shared state

Couplings never keep a private copy of a quantity another coupling needs.

  • SurfaceBus (case.bus, per column): Ts, sw, lw, the extra surface loss sensible (energy other couplings take from or give to the surfaces this step — window sun, glazing transmission, dew heat; not the turbulent sensible flux), the dew reservoir dew, the clear-sky beam sw_beam, the per-class params, the last radiosity solutions swsol/lwsol, the sky longwave L_sky and the direct/diffuse shortwave dni/dhi the :column_radiation slot hands the radiosity solve (#130; NaN shortwave means "Bird"), and (#129) the per-column surface (AbstractSurface), the roof-aware air level k_air, the forcing each surface last saw (T_air, q_air, U, z_ref), the fluxes it returned (Rn, H, LE, G, E, u_star) and the dew_mask.
  • Surface factories. A coupling that provides the surface of a class registers register_surface_factory!(case, class, name, (case, site) -> surface) in its build, where site::SurfaceSite carries the class, the initial skin temperature, the child column (nothing for a tile of a parent column) and an optional roughness override (take the roughness from class_roughness(case, site)). class_surface(case, site) is the one class-to-surface factory: the surface exchange builds every child column's surface with it in its init! (a SlabLand for a class nobody claims), and the parent's tiled surface (#249, below) every tile. This is how the park (#140), water (#141) and facet (#139) couplings replace a class's surface — in the child and the parent at once — without touching the surface exchange.
  • Tracers (case.tracers): ensure_tracer!(case, :qi; advect = true, positive = true, units = …, long_name = …) creates or returns a cell-centred field; flags are OR-ed, so two couplings share one ql. The :transport stage advects every tracer with advect = true in registration order, and every tracer with output = true is written to the NetCDF file. The core registers qv, ql (advected) and qr. A tracer diffuses with the closure's κt unless it names its own diffusivity (ensure_tracer!(…; diffusivity = case -> field)): the SGS TKE e of the :tke provider diffuses with 2ν_t (#182). Passive tracers (qv, ql, the chemistry species, the pollutant) never name one: they share θ's κ_t under every :sgs provider, AMD included (#234, see below).
  • Geometry (case.geom): mask, surface classes, scene, view factors. Couplings may add classes at init! (the glass coupling does). The scene is built with class_map = scene_class_map(sfc), so the ground facet of every open column has the material of its class (park, water, street; wall-tagged cells are street ground).
  • Reference state (case.ref, see below): the hydrostatic p̄, ρ̄, T̄, Π̄ per level. Every coupling that needs a pressure, converts a flux into a mixing-ratio or θ increment, or turns θ into T takes it from here (ref_pressure, ref_density, ref_exner, surface_pressure, ref_ρcp), never from a constant of its own.

Modifying bus.sw. The radiation provider writes bus.sw only at the radiation cadence; the :sw_modifiers stage runs every step. A modifier must therefore act on the unmodified field, not on its own previous output. sw_modifiers keeps that field (sw_base), takes a new one whenever bus.sw differs from what it wrote on its previous step, and rebuilds bus.sw = cloud(shade(sw_base)) each step. A second modifier added later belongs in the same pattern. Before #128 the tree shade and the cloud shadow multiplied bus.sw in place, so they compounded between radiation updates.

Checkpointing the case's own state is #269 / #134; the hook is described in Checkpoint / restart.

Initial state: the Lindenberg sounding (#247)

Until #247 the case started from an analytic profile, θ = 293 K up to 100 m and +3 K/km above, with $q_v = 10\,{\rm g\,kg^{-1}}\,e^{-z/800\,{\rm m}}$ and 1013.25 hPa at the ground. #238 showed that this profile cannot cap a convective boundary layer, and the nesting parent (epic #246) must start from the same observed state as the child. The summer case now starts from the radiosondes of the Lindenberg observatory (WMO 10393, 60 km south-east of Alexanderplatz).

Case day. The epic first named 20 June 2024. That day was overcast (DWD hourly total cloud cover 7–8 oktas most hours at Lindenberg and Berlin-Tempelhof; the 12 UTC sounding is saturated at 907 hPa), so by the maintainer decision of 2026-10-05 the case moved to 29 June 2019, a clear day of the late-June 2019 heat wave: 0–2 oktas at Lindenberg and Berlin-Brandenburg from 00 UTC on the 29th to 16 UTC on the 30th, and a 12 UTC dew-point depression of at least 6 K below 700 hPa. The day is a Saturday; case_weekday(cfg) now feeds the weekday of cfg.date to the building schedules (they assumed the Thursday of 20 June 2024 before).

Data. examples/urban/data/fetch_lindenberg.jl downloads the IGRA2 record of GMM00010393 from NOAA NCEI (public domain; Durre et al. 2018) and writes lindenberg_10393_20190629.csv: the 00/06/12/18 UTC launches of 29 June and the 00/06 UTC launches of 30 June, with pressure, reported geopotential height, T, T_d, wind and the IGRA QC flags. Its header records the URL, the download date, the station elevation (launch site 112 m, not the 97.7 m of the IGRA station list: with 97.7 m every launch misses the reported heights by 11–19 m) and the case-day check. The profiles are the GTS standard and significant levels, not the full-resolution BUFR ascent.

Profiles (src/large_scale_forcing/sounding.jl). read_sounding reads the CSV; sounding_profiles(s; z_top) returns θ, $q_v$, u, v and p as ForcingTables on heights above the launch site and the release times. Heights are hypsometric (virtual temperature from MoistThermodynamics), θ uses its Exner function and $q_v$ its $e_s(T_d)$; no thermodynamics is defined in the reader. The reported geopotential heights are used only as a check: below 3 km the computed heights match them to RMS 0.8–4.3 m per launch, within the ±4.7 m that the whole-hPa surface pressure of the GTS message allows.

The case (core/reference_state.jl). initial_θ(cfg) remains the one definition of the initial θ: forcing_value of the θ table at the case start, 06:00 CEST = 04:00 UTC, which lies between the 22:45 and 04:45 UTC releases (weight 0.875 on the later one). initial_qv(cfg) does the same for $q_v$ and replaces the inline exponential of build_case. case_surface_pressure(cfg) reduces the launch-site surface pressure from 112 m to the case's 34 m with the surface virtual temperature. build_reference integrates from it, and so does every consumer of the reference state, the nesting parent included. The heights of the sounding are used as heights above the case's ground: the profile is taken as horizontally homogeneous over 60 km and as terrain-following over the 78 m elevation difference.

The smoke matrix also runs "summer sounding, everything on", the smoke box started from the sounding at noon, so the observed path is exercised by every suite run.

The boundary-layer height. zi comes from `TurbulenceStability.boundarylayerheighteverywhere: soundings, the CBL harnesstest/tkecbldriver.jl` and the nesting diagnostics. It is the only zi diagnostic in the package; see Stability functions and the gradient Richardson number.

Reference state and moist buoyancy

The Boussinesq core carries neither pressure nor density, and before #131 each coupling assumed its own: fog and dew an isothermal 8 km scale height from 1013.25 hPa, the surface, building and traffic fluxes and the ledger ρ = 1 (ρcp = 1005). Since #131 core/reference_state.jl builds one hydrostatic profile per case, Aeolus.Anelastic.reference_from_profile of the initial θ(z) (see the initial-state section above) from case_surface_pressure(cfg) (1018.4 hPa at the ground on the summer case day since #247; 101 325 Pa for the idealised profile), with the dry-air constants of MoistThermodynamics (so T = θ Π̄ is the temperature the fog adjustment and the saturation functions assume) and the g of the dynamics. It is exactly (1e-12 Pa m⁻¹) in the discrete balance of the anelastic core and 5e-8 from an RK4 integration of the continuous hydrostatic equation. The isothermal profile it replaces was 0.17 % off at the flagship's top level; the density is 1.20 kg m⁻³ at the ground in summer, 1.30 in winter.

Moist buoyancy (couplings/moist_buoyancy.jl, on by default). The core adds only the dry buoyancy g (θ − θ₀)/θ₀ (sim.moisture = false: the water lives in the tracer registry). In :body_force the coupling adds the rest of the density-potential-temperature buoyancy,

g (θ_ρ − θ)′ / θ₀,     θ_ρ = θ (1 + q_v/ε − q_t) ≈ θ (1 + 0.608 q_v − q_c),

from MoistThermodynamics.density_temperature, at every interior w face (the two adjacent centres averaged, as the core does for θ). The prime is the deviation from the mean over the fluid cells of the level: a horizontally uniform force is a pure pressure gradient in the incompressible core, so subtracting it only changes the diagnosed pressure. The condensate q_c is every tracer the ledger counts as water other than qv (ql and qr today), so a microphysics provider that calls water_tracer! has its species loaded without touching this coupling. It writes b_moist (m s⁻²) to the NetCDF file and a report line (rms and max of b′, max RH and min dew-point depression of the lowest layer).

In the flagship configuration (1 h from 06:00, no fog) it costs 0.86 ms/step. At the end of the hour the rms moist buoyancy is 8.8e-4 m s⁻² (max 1.8e-2, the buoyancy of 0.5 K), a quarter of the rms dry buoyancy perturbation (3.6e-3). In the same hour run without the coupling, the moist buoyancy the state would have is twice as large (rms 1.8e-3, max 3.4e-2): with the term on, the light, humid air the buildings and surfaces release rises and mixes instead of accumulating as anomalies. The two runs also differ in the minimum level-1 humidity (4.8 g/kg with, 3.3 without) and in dew deposition (1.6e-3 against 2.9e-3 kg m⁻²), but after an hour of turbulence part of that is the divergence of two chaotic runs, not the term alone.

Adding a coupling

This is the whole procedure. It touches one new file and the PR body; no shared file of the case is edited.

1. Put the physics in src/. A coupling only wires a src implementation into the 3-D run. If the physics is missing, add it to the right src module with its own tests first. Never copy it into the example.

2. Write examples/urban/couplings/<name>.jl. One struct, the contract methods it needs, and register! as the last line:

# P3 microphysics (Aeolus.P3Microphysics) in the :microphysics slot.

struct MicroP3{W} <: AbstractCoupling
    work::W
end

coupling_name(::Type{<:MicroP3}) = :micro_p3             # unique; key in cfg.options
slot(::Type{<:MicroP3})          = :microphysics         # or :addon
provider(::Type{<:MicroP3})      = :p3                   # cfg.physics[:microphysics] = :p3
is_default(::Type{<:MicroP3})    = false                 # an alternative: off by default
modules_used(::Type{<:MicroP3})  = (:P3Microphysics,)    # the Aeolus modules it runs
default_options(::Type{<:MicroP3}) = (skip_dry = true,)
stages(::Type{<:MicroP3}) = ((:microphysics, 10, EVERY_STEP),)

function build(::Type{<:MicroP3}, case, o)
    ensure_tracer!(case, :qi; advect = true, positive = true, units = "kg kg-1",
                   long_name = "ice mass")               # transport picks it up
    return MicroP3(...)
end
init!(c::MicroP3, case) = water_tracer!(case.ledger, :qi) # count it as water

function run_stage!(c::MicroP3, case, ::Val{:microphysics}, dt)
    ...                                                  # calls into Aeolus.P3Microphysics
end

budget!(c::MicroP3, case, l) = add_water!(l, :precipitation, -c.surface_precip_step)

smoke_check(c::MicroP3, case) =
    ["ice ≥ 0" => minimum(interior_view(tracer(case, :qi))) >= 0,
     "precipitation ≥ 0" => c.surface_precip_step >= 0]

register!(MicroP3)

The file is picked up by the directory scan; include order is the sorted file name, which is also the registry order (and the tie-break between entries of the same stage and order).

  • On by default. An additive coupling is on unless is_default says otherwise; a slot provider is the slot's default only if it is the one with is_default = true. The rule of #123: new physics is on by default unless it is a genuine alternative or too expensive, and then its cost per step is quoted from timing_report in the PR.
  • Cadence. An expensive stage can run every P seconds: Cadence(600.0), or Cadence(:mykey) with a default in cfg.cadence (add the key through the scenario or your option; a missing key is an error). Stages inside step! (:body_force, :post_predictor) must run every step.
  • Shared state goes through the bus, the tracer registry and the geometry, never a private copy (see above). If you need a bus field that does not exist, add it to core/bus.jl additively and say so in the PR.
  • Replacing a coupling. Delete the old file (the issue says which) and move its budget! terms and checks over. The ledger closure in the smoke test fails if a term that changes a surface temperature or the water in the air is lost.

3. Report to the ledger. If the coupling changes a surface temperature, adds or removes water from the air, or clips anything, book it in budget! (next section). The smoke test asserts the closure, so a missing term fails the suite.

4. Give it smoke coverage. The smoke test already runs every additive coupling and one configuration per non-default provider, so most couplings need no smoke_variants. Add one for a configuration that is not reached that way, for example an option that changes the code path:

smoke_variants(::Type{<:MicroP3}) =
    ((label = "sgs cloud on", physics = Dict(:microphysics => :p3),
      options = Dict(:micro_p3 => (sgs_cloud = true,))),)

Each variant is a NamedTuple: label, then physics and options (merged into the everything-on configuration), then any CaseConfig field (nsteps = 30, size = …). Write smoke_checks that assert physics: a conservation or a budget, a bound that follows from the equations (a maximum principle, positivity, a range set by the thermostat), a sign that follows from the physics. "It ran" is already asserted for every coupling.

5. Run and quote. julia --project=. test/berlin_smoke.jl locally (under a minute), then the full suite. In the PR body quote one Berlin diagnostic — a ledger term is often the natural one — the configuration it was measured in, and the cost from timing_report.

Validation of the refactor (#126)

The refactor had to be bit-for-bit. On a 1 h run (AEOLUS_NSTEPS=1800, two records) every NetCDF variable of the refactored case is identical (==) to the pre-refactor script, and the printed frame lines match apart from the wall-clock column.

The pre-refactor script is not reproducible run to run. Two 1 h runs of the same old script, one with a freshly measured FFTW plan and one with an imported plan, differed by up to 7.5e-9 m/s in w, 4.7e-10 m/s in v and 6.0e-8 in the pollutant (Float32 output; θ, moisture and the surface fields happened to agree). The cause is FFTW.MEASURE in the cosine-FFT pressure solver: the planner times candidate algorithms and may pick a different one in each process, with different round-off, which the flow then amplifies. With the same FFTW wisdom imported into both processes (FFTW.import_wisdom) the planner is deterministic, and old and new cases then agree exactly in every variable. Bit-for-bit comparisons of the Berlin case have to fix the FFTW plan this way.

Found during #126, fixed in #132: stale velocity halos in the scalar transport. step! corrects the interior velocity after the pressure solve but leaves the halos at the predictor values. The Berlin case advects its scalars (qv, ql with WENO-Z5, the pollutant with centred differences) at the start of the next step, on those halos, so the velocity it sees is not divergence-free across the periodic seam and the flux form stops conserving: in the :smoke window after four steps the transport stage changes the domain total of qv by −4.4e-5 and of ql by −3.5e-5 per step. With the halos refreshed (fill_halos! on u, v, w) the same stage conserves both to 1.5e-15 and 3.8e-15. The fix changes the answer, so it is not in #126; test/berlin_case.jl records the leak as @test_broken and asserts the conservation with fresh halos. The scalar-advection issue (#132) owns it.

The ledger (#127) measures the same leak in water. On step 1 it is much larger: the velocity halos have never been filled when the transport first runs (set! fills only the interior), and in the :smoke window the first transport step adds 7.5e-3 kg m⁻² of water, 0.8 % of the water in the air (9.4e-1 kg m⁻²); every later step removes about 3.5e-5 kg m⁻². With the halos refreshed the same steps change the water by at most 1.3e-15 kg m⁻². Over the 1 h flagship run the transport term is −2.70e-4 kg m⁻². Fixed in #132: the scalar_advection coupling refreshes the u, v, w halos before it advects (refresh_halos = true), which also gives the pollutant, which advects later in the step, fresh halos. The water change of the transport stage is now ~1e-19 kg m⁻² per run (smoke) and +6.9e-19 kg m⁻² over the flagship hour; both @test_broken are now @test, and test/berlin_case.jl keeps the mechanism tested with refresh_halos = false.
