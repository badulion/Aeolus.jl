The kernel port (KernelAbstractions)

Aeolus runs single-node multithreaded through KernelAbstractions.jl (KA), with one kernel path that a GPU backend will reuse in Phase 81 (port plan #291, maintainer decision 2026-10-06). This page is the contract every port PR follows. KA-a (#294) laid the foundation: the dependency, src/Backends.jl, set! / interior_map! as the first kernels, the deterministic reductions and the thread-invariance harness. The API is under Compute backends.

Rules of the port

  • All KA code lives in src/Backends.jl. Every @kernel is defined there. The rest of the code base writes plain Julia bodies and calls launch!.
  • Bit-for-bit means N threads = 1 thread on the new code. A pointwise kernel also gives the same bits as the loop it replaces. A call site that moves to a canonical reduction changes its bits once against today's master. That is allowed only where the port plan names it (canonical reductions, CG/MG iteration counts, the WENO power fix, the TKE / IBM wall-stress / radiosity gather rewrites), and the PR reports the change with numbers.
  • Gate per port PR: 1-thread time ≤ 1.10× the loops it replaces. Quote the 4/12/24-thread speed-ups too.
  • Every port PR runs the thread-invariance harness and quotes it (below).

Backends

CPUBackend()                       # KA.CPU() on Julia's threads (julia -t N)
CPUBackend(serial = true)          # every launch on the calling task
CPUBackend(threshold = 0)          # thread even the smallest launch (tests)
GPUBackend(:cuda)                  # stub until Phase 81: errors on use

default_backend() is the backend new fields are allocated on: Field(loc, mesh; backend = default_backend()) allocates through allocate(backend, T, dims). backend(field) gives a field's backend. init_threads!(backend) makes backend the default and sets the library thread counts (below). with_backend(f, backend) runs f under a temporary default; it is process-global, not task-local. The Berlin case takes its backend from CaseConfig.backend and calls init_threads! first thing in build_case; every other run gets it from Config.build (#524: until then a model domain's FFTs ran on one thread).

The launch contract

@inline function axpy_body!(i, j, k, y, a, x)
    @inbounds y[i, j, k] = y[i, j, k] + a * x[i, j, k]
    return nothing
end
launch!(backend, axpy_body!, interior(mesh), y.data, a, x.data)
  • Ranges are storage indices (halos included), as a tuple of UnitRange{Int}s. Any region is one launch: the interior (Hx+1:Hx+Nx, …); a face range with one more point (Hx+1:Hx+Nx+1); an extended range into the halo (Hx:i2); a halo shell (1:Hx, …); a 2-D surface range (i, j) with body!(i, j, args...); or a 1-D range of ids (surface elements, particles) with body!(n, args...). The body gets the storage index and does its own offset arithmetic (xs[i - Hx]).
  • The body writes only point (i, j, k) of its outputs. It may read its inputs anywhere, but never something another point writes in the same launch. An in-place stencil therefore needs a scratch array (see scratch rules).
  • Everything the body reads is an argument. Do not close over globals. Closures over local values are fine ((y, x) -> y + a*x).
  • The body carries its own @inbounds. launch! does not check bounds. The public wrappers (set!, interior_map!, range_map! and the reductions) check the whole range once per call.
  • The result must not depend on the order points run in. Accumulate only through the reductions below, never through a shared variable.

Two performance traps that the 1-thread gate caught in KA-a. Both gave correct results and were only slow.

  • Specialisation. Julia does not specialise a pass-through args..., or a ::Function argument that is only handed on. A wrapper written as foo(f::Function, args...) = launch!(b, body!, r, f, args...) is compiled for Function / Any, and the loop then dispatches at every point: 375× the loop for an axpy, 17× for set!(f, g). Write wrappers as foo(f::F, args::Vararg{Any,M}) where {F, M}. launch! itself forwards its arguments as one type parameter.
  • Aliasing. If the same array reaches the body through two arguments (interior_map!(f, y, y, x): out and an input), the compiler cannot prove the loop free of dependences and keeps it scalar (1.8×). range_map! therefore reads an input that is out through out. Hand-written bodies should take an in-place array once.

How a launch runs. The loops run on the calling task, in the historical order for k, for j, for i, when the backend is serial = true, when Julia has one thread, or when the launch covers fewer than threshold points (default 32 768, a 32³ block: a task start costs a few µs per thread). This is also why a -t 1 run executes exactly the loops it executed before the port. Otherwise the launch is a KA kernel whose work item is one i-row, in workgroups of four rows (the (n_i, min(n_j, 4), 1) block of the plan). KA's CPU backend splits the workgroups into nthreads() contiguous chunks, one task each.

Why rows and not points: on KA's CPU backend a point-per-work-item kernel computes a Cartesian index per point and does not vectorise. For an axpy at 64×64×32 at one thread it measured 5.9× slower than the plain loop (119 vs 20 µs), and 2.0× at 256³. The row kernel keeps the inner i loop a plain loop the compiler vectorises. A GPU backend will launch the same body one point per work item; the body is the portable unit, not the iteration strategy.

The arguments reach the loop as arguments (KA-d, #299). A large body with branches (WENO-5, the tensor-diffusion face fluxes) inlined into a loop that reads its arguments out of the args tuple ran 3-5× slower than the same body in a plain loop (WENO-5 at 64×64×32, one thread: 6.3 ms against 2.1 ms): LLVM did not hoist the array loads behind the branches. Arrays that arrive as function arguments are known dereferenceable, and then it does. So the serial path calls _nest!(body!, ir, jr, kr, a1, …, aN), the whole k/j/i nest in one function with the arguments separate, and the threaded row kernel calls _row!(body!, ir, j, k, a1, …, aN) per work item. Each argument has its own type parameter (a function among them is still specialised; methods are generated for up to 24 arguments, plain loops beyond). Same operations in the same order, so no bit changes. Small kernels are unchanged at one thread (axpy 22-24 µs, set! 11 µs, the Laplacian 46-47 µs at 64×64×32); WENO-5 went from 6.3 to 2.0 ms at one thread and from 0.83 to 0.39 ms at 12. A call per row on the serial path instead of one per nest made the Laplacian 1.3× the old loop, hence _nest!. A 2-D launch on the serial path calls _nest2!(body!, ir, jr, a1, …, aN) the same way (KA-e, #302): boundary_scalar_flux's face bodies (up to 19 arguments) ran 2-2.5× the old loop when they read the tuple.

Column kernels: launch_weighted! (KA-h, #298). A body that loops over a whole column itself — a tridiagonal solve in z, serial within the work item — does Nz points of work per index, so a launch over (i, j) or over rows j would look small to the threshold and to the points-per-task rule (a 64-row launch is 64 "points"). launch_weighted!(b, weight, body!, ranges, args...) is launch! with those two rules counting weight × length(ranges) points. Same contract, same serial order. It is not a per-kernel cost hint: the weight is the number of points an index covers.

A column per work item can be slow on the CPU: the column walks z with a stride of Nx·Ny·8 bytes, a power of two on the usual grids, so all its levels fall in the same L1 set. StretchedPoissonSolver's Thomas solve with one column per item took 4.3 ms at 64×64×53 against 0.94 ms for the whole old solve. One ky row per item (kx innermost, vectorised) fixed most of it, but the Thomas part alone still cost 1.2× the old loop at 64×64×53 and 1.6× at 192×192×53 on one thread: Nx contiguous values per level are too short a stream for the prefetcher. The work item is therefore a contiguous slab of ky rows, walked in the old loop order (level by level, kx innermost), with one slab per thread and a single slab, the old loop exactly, when the launch runs serially. The slab count may follow the thread count because every column is still solved by one work item with the same operations, so the bits do not depend on it. A GPU backend will launch one column per item.

The reduction contract

Sums over a region use one canonical order that does not depend on the thread count:

  1. Within a plane (fixed k), rows are taken in ascending j. Each row is reduced in eight lanes. Point i of the first 8⌊n/8⌋ goes to lane (i − i₁) mod 8, and the rest of the row goes to lane 1 in ascending i. The lanes are combined as ((l₁+l₂)+(l₃+l₄)) + ((l₅+l₆)+(l₇+l₈)).
  2. Planes are combined in ascending k by ordered_sum, a strict left fold.

Each plane is reduced by one work item, so the plane partials, and everything built from them, are identical serially and at any thread count. The eight independent lanes let the compiler use SIMD and hide the add latency without reassociating anything. test/backends.jl checks the implementation bit for bit against an independent transcript of this rule.

plane_reduce! is the general form. Its body follows the launch contract: it may read a stencil (a strain rate, a centred w), may write its own point (an update fused with the sum of what it changed: a chemistry step returning its production), and takes per-level coefficients as arguments indexed by k. A masked mean is a tuple body returning (value, 1.0) or (0.0, 0.0): adding an exact 0.0 leaves a lane unchanged, so the masked sum is the canonical sum of the masked values. Ranges may be storage indices of halo-padded arrays or axes of interior-sized views. A range_max body only reads: its result type is inferred (Base.promote_op), never found by evaluating the body an extra time.

plane_map! is the escape hatch for a reduction where the eight lanes cost more than they gain: the plane function runs its own loop (one running sum in cell order, i fastest) and each plane is still one work item, so the partials are thread-invariant. Its only user is apply_wet_deposition! (below): exp is called in the raining cells only, and keeping eight lanes live across that call made the fused update 1.3× slower than the old loop at one thread.

Implementation. For Float64 sums the eight lanes are the eight elements of one <8 x double> vector (an llvmcall fadd): point i₁ + 8b + r goes to element r, so a plane is one vector add per eight points. The vector add is eight independent IEEE additions, so the bits are those of the scalar lanes (test/backends.jl checks the transcript); the compiler does not vectorise eight scalar accumulators by itself, and the vector form measured 2.4× faster (interior_sum 23.3 → 9.6 µs at 64×64×32, one thread). Other element types use the scalar lanes. Maxima need no canonical order (max is exact and commutative), so interior_max and range_max scan a plane in a plain loop: their bits equal those of any serial maximum.

Surface (2-D) sums over the (i, j) columns stay serial: a loop over the columns folds their contributions in column-major order (for j, for i), or Base sum reduces a finished 2-D array. Both run on one task, so they are thread-invariant; a threaded kernel that produces the per-column values keeps the serial sum after it (a few µs at 64×64).

Per-level loops that already reduce one plane at a time in a plain for j, for i loop (the dynamic-Smagorinsky plane averages, the #288 damping levels, the large-scale forcing's nudging and subsidence plane means) are thread-invariant as they stand, because a plane is one work item, and are left unchanged and documented as canonical.

The canonical order is not Base's. sum(view(A, I...)) over a non-contiguous view is a plain sequential sum, so it is not just different, it is less accurate. For Σ θ² of a 37×29×23 linear profile the eight-lane order is within 3.1e-16 of the exact (BigFloat) value, and Base's sum(abs2, view) within 2.9e-13. Moving a call site to the canonical order is therefore a named one-time bit change, and the PR quotes its size.

Scratch rules

  • A kernel that reads a neighbour of what it writes uses a separate output array (a tendency, a lap_* field, a workspace). Allocate it once with the simulation, not per launch.
  • Per-work-item temporaries are locals (registers / stack), never a shared buffer indexed by thread id: KA gives no stable thread id, and the work-item → task map changes with the thread count.
  • Partials arrays for reductions are sized by the outer range (n_k planes, n_i × n_j columns), not by the thread count.
  • Random numbers: never one generator shared by the work items of a launch (the draws would depend on which task got there first). Each item makes its own stream from what identifies it, counter_rng(key, stream, id) for a few draws or counter_xoshiro for hundreds, keyed by a seed or one draw from the caller's rng (KA-n). Tallies go into per-item buffers merged in item order.
  • A column work item (foreach_column!, KA-m) owns its scratch: a workspace that belongs to the column's own object (a soil column's, a facet's conduction column), or vectors the column allocates itself (a raining Kessler column's col / Nr). Never one buffer captured by a closure and shared by every column, and never a global scratch vector (the Mie log-derivative buffer was one, and raced, until KA-m made it task-local).
  • Lazily filled global caches are filled before any launch can reach them, or guarded by a lock (KA-m): the Gauss-Legendre nodes are a table computed when RadiationCore loads, the aerosol optics memo and the SNICAR table are locked.

FFTW and BLAS

  • FFTW plans come from the #245 policy (set_fftw_policy!): MEASURE by default, PATIENT opt-in, ESTIMATE in the tests (set by test/runtests.jl and inherited by every subprocess, including the harness). ESTIMATE plans are deterministic. Since KA-h (#298) init_threads! sets the FFTW thread count to Threads.nthreads(), through that policy, so fftw_policy() and the checkpoint record report it. A count chosen explicitly wins: init_threads!(b; fftw_threads = n), AEOLUS_FFTW_THREADS, set_fftw_policy!(threads = n) or a namelist's [fftw] threads. Call init_threads! before the simulation is built: a plan keeps the thread count it was made with.
  • Threaded FFTW is thread-invariant under ESTIMATE. FFTW's threaded plans hand whole 1-D transforms (and contiguous slabs of them) to the threads and leave each transform's arithmetic unchanged. Measured at KA-h: every pressure solver (FFT, CosineFFT with each of the 8 axis-BC combinations, Stretched with each of the 4 lateral pairs) gives bit-identical solves with plans made at 1, 2, 4, 12 and 24 threads, at 64×64×32, 128²×64, 192²×53, 256²×128, 96×80×40 and 37×29×23. Under MEASURE the planner times candidates per thread count, and the same check found differing bits in 3 of the 13 solvers at 64×64×32 (for 2, 12 and 24 threads). MEASURE runs are not bitwise reproducible anyway (#245), and imported wisdom made at the same thread count restores reproducibility. The pencil-parallel fallback the plan held in reserve (serial 1-D plans launched over pencils) was not needed.
  • Transforms run from the host. Plans are executed through apply_transform!(backend, out, plan, in) between kernel launches, never inside a kernel, so a GPU backend can put cuFFT behind the same call (Phase 81).
  • BLAS is pinned to one thread whenever Julia runs threaded (the accepted default on #294): BLAS threads would oversubscribe the cores next to the kernel tasks. The dense solves (the radiosity LU and its solves, the direct facet solve), which run while the kernels wait, use Backends.dense_blas_threads() for their duration (#496; OpenBLAS's default, its physical-core count, unless blas_threads or OPENBLAS_NUM_THREADS says otherwise). Under -t 1 the BLAS setting is left alone. (Bit-identity across BLAS thread counts is not a goal since epic #493.)

The thread-invariance harness

test/thread_invariance.jl has two levels:

  1. In process (always): the reductions and a 3-step 32³ Boussinesq run with CPUBackend(serial = true) against the threaded backend. This is meaningful when the suite runs threaded (test/run.jl --threads 4).
  2. Subprocesses (opt-in, AEOLUS_THREAD_TESTS=1): test/support/thread_invariance_worker.jl runs at julia -t 1/4/24 (AEOLUS_THREAD_COUNTS). It hashes the raw bits of: the primitives on seeded fields (NaN / Inf included); every field of a 64³ Boussinesq DNS after 2 steps; and every run of the Berlin smoke matrix (12 steps) plus one step of the 64×64×32 flagship. For each Berlin run it hashes every simulation field, tracer and surface-bus array, the surface / water / air-heat ledgers, the dt sequence and the pressure-solver iteration counts. Every hash must equal the 1-thread hash, and the differing keys are listed otherwise.
AEOLUS_THREAD_TESTS=1 julia --project=. test/run.jl --only thread_invariance.jl

Later port PRs extend the worker with their own sections, not the driver. KA-m added columns: the column kernels on seeded inputs, every launch threaded (threshold = 0), BLAS on one thread in that section (see "Measured at KA-m").

Without that cap the 64×64×32 axpy took 67.6 µs at 24 threads, 2.7× the serial loop. A pure store (set!(f, value), 11 µs) is still slower threaded at 12 and 24 threads.

KA-f: halo fills, open boundaries and nesting transfer (#297)

Halo fills. Every phase of fill_halos! — periodic, mirror, the free-slip and no-slip walls, the free-stream top, the fixed-gradient top, and the open faces in :value, :odd, :mirror and :inflow mode — is one launch! of a point body over the face slab (src/boundary_conditions/halo_kernels.jl). A slab is layers × the full extent of the two tangential axes, so edges and corners are filled too. The phases run in the old order: x, then y, then z, and within an axis the faces in their old order. An edge or corner therefore keeps the value of the last axis that reaches it, and test/ka_halos.jl checks this ("corner order").

A phase on the pencil normal to a face reads only that pencil, and the old loops ran its layers in ascending h. Two cases follow:

  • A one-sided phase reads the interior side of its face, plus the face slot written by an earlier launch, and writes only beyond the face. It is always independent.
  • A two-sided phase (periodic, or mirror on both faces) can read its own writes when the interior is shallower than the halo (N < H, e.g. a 2-D run with Ny = 1). Such a launch runs on the calling task in launch!'s serial order, which keeps ascending h per pencil. The result is then the old one at every thread count.

Along x the layers are the contiguous direction, so a work item is one x-pencil whose layer count is a compile-time constant (1–4). The first version used a 3-D launch with the layer as the innermost loop, and it made the multigrid halo (H = 1) 2.7× the old plane copies.

The multigrid level halo (Multigrid._fill_halo!) is the same periodic and mirror kernel with H = 1: one source with fill_halos!. The open faces no longer box their plane when they look it up, so an open fill allocates 0 B (it was 0.8–3.4 kB per call).

Radiation outflow. The phase speeds, the stage mark and the upstream update of a convective or Orlanski face are launches over the face points. In the radiation update a work item owns its buffer pencil.

Nesting. Owner computes for every write:

  • Prolongation: each child point interpolates from its parent stencil, one launch per box (and per slab of a halo-only shell).
  • Limiters: per box, each parent cell gathers the extrema of its children. This was a scatter into the parent arrays. max and min return one of their operands, so the order of the children does not change the bits. Then the factor is computed per parent cell, and the scaling and the face clip per child. A plan now carries the inverse of its cell map, the contiguous children of each parent cell.
  • Restriction: each covered parent cell or face gathers its children. This covers the volume and mass measures, the solid-aware case, cells and faces.
  • Per parent face or cell: the flux mismatch, the face flux correction and the refluxing. Refluxing finds the parent cell beyond a face with neighbor_index instead of mod1. The same holds for the two-way anterpolation, interface correction, register mismatch and bookings.
  • Pointwise: the sponge and the boundary-data time blend (blend_window!).

The interface-imbalance L1 sum stays a serial loop. It is a diagnostic, and moving it to a canonical reduction would change its bits. The synthetic-inflow RNG is not touched (seeded per face, serial).

Bit for bit. Every BC type, combination and location matches the pre-port fill on random fields with random halos, at 12×10×8, at 9×7×6 with halo (2, 4, 3) and at 5×1×2 with H = 3. This holds on the serial, threshold-0 threaded and default backends. The reference is a transcript of the old plane copies (test/support/legacy_halos.jl). Likewise 124 transfer-operator calls match the pre-port operators (test/support/legacy_nesting.jl). The covered cases are orders 1, 3 and 5, the three limiters, halo / interface / whole-child regions, solid-aware and mass-measure restriction, and the flux mismatch and correction. KA-g: one CG driver (#300)

One loop. Backends.pcg! is the only preconditioned conjugate gradient in Aeolus. CGPoissonSolver, MGPreconditionedCG, DensityWeightedPoissonSolver and solve_implicit_diffusion! (the IMEX steppers' implicit diffusion) call it. Their own loops are deleted: _dot!, _project_mean_flat!, Anelastic's _dot, _remove_mean! and _jacobi!, TimeIntegration's _apply_implicit! and _idot. A solver supplies four things:

  • the operator: a PointOperator(f, args...; prepare) (the stencil at one point; prepare is the halo fill of the array it reads) or a function A!(Ap, p) (the multigrid fine-grid operator);
  • the preconditioner: IdentityPreconditioner(), a pointwise PointPreconditioner (Jacobi), or a function M!(z, r) (V-cycles);
  • project_mean for a singular operator (all axes periodic or Neumann);
  • constraint: the pinned planes of a staggered field with walls.

Per iteration the driver makes three sweeps and two canonical reductions:

  1. Ap = A p, with p·Ap reduced over each plane while it is in cache;
  2. x += αp, r -= αAp, z = M⁻¹r (a pointwise M), with (r·r, r·z, Σz, Σr) as one 4-tuple reduction;
  3. p = (z − m) + βp, where m = Σz / n with the mean projected out.

The mean projection costs no extra sweep: r·z of the deflated z is Σ rz − m Σ r. The density-weighted solver went from nine passes over the arrays per iteration (five sweeps and four separate reductions) to three sweeps carrying two reductions. A function preconditioner adds one reduction after M!. Every reduction is a plane_reduce!-style plane sum, so a solve, its iteration count and its residual are the same at every thread count.

Unit halos. CGPoissonSolver and DensityWeightedPoissonSolver now keep b, x, r, z, p and Ap as (N+2)-arrays with one halo layer. fill_unit_halo! (the KA-f halo kernels, also the multigrid level halo) fills the periodic wrap or the Neumann mirror before each operator application. The stencil then has no wrap-around index arithmetic and vectorises: one point of _laplacian_at and _neg_wlap_at gives the values of the old wrap-around loops (a mirrored neighbour makes the face difference exactly zero). The implicit diffusion iterates on the field's own storage as before, with fill_halos! as prepare. _diffusion_kernel! is a launch! of _diff_at.

Pinned rows. A per-point pinned test in the sweeps stopped the row loops from vectorising: 4× slower in a first version. The sweeps therefore compute every point and then zero the pinned plane (Ap, z and p there are 0, x keeps its value, b there does not count in ‖b‖), as _apply_constraint! did.

Status. pcg! returns (iterations, residual, bnorm, status, curvature). status is :converged, :maxit, :breakdown or :zero_rhs, and each solver logs it as before. One change: CGPoissonSolver now stops at a breakdown and warns. Before, it divided by a vanishing p·Ap and went on. definite = :negative is for the two Poisson solvers that iterate on ∇² itself (negative semi-definite). For those only a vanishing curvature is a breakdown.

Workspace. PCGWorkspace holds r, z, p, Ap and the per-plane partial sums. Every solver preallocates one, so a solve allocates nothing on one thread. Measured with @allocated, the Poisson solvers allocate 0 B. solve_implicit_diffusion! allocates 48 B (352 B with a moving wall), the same as before; the 48 B are its returned NamedTuple at a dynamic call site. A first version allocated 80 B more with a ν array: the Union of the two preconditioners was boxed. It now has one pcg! call per preconditioner. Above the serial threshold a threaded launch allocates KernelAbstractions' tasks, about 9 kB per iteration at 4 threads.

The iteration counts did not change: identical in all 28 cases measured (the 14 below at 32×32×16 and 64×64×32; the issue allowed ±1). KA-i: the multigrid V-cycle (#303)

Kernels. Every loop nest of MultigridPoissonSolver and of the V-cycle preconditioner of MGPreconditionedCG is a launch! of a pointwise body, and every sum a canonical plane reduction:

  • _smooth_rbgs!: per colour, the halo fill and then one launch over that colour's cells only. The launch covers half of each i-row; the index ih maps to i = 2ih + ((j + k + colour) & 1), so (i + j + k) & 1 == colour. It is still red-black Gauss-Seidel. The cells of a colour read only the other colour, so the order they run in does not matter and the sweep has the bits of the serial loop. For an even nx every row has nx/2 cells of a colour and the body has no bounds test. The strided loop then vectorises: one colour at 128×128×64 takes 0.65 ms instead of 1.19 ms with the test, and 1.49 ms for the old "skip by parity" loop over all cells. An odd nx keeps the test.
  • _compute_residual! (constant and variable coefficient: one body, the operator passed as _ConstOp / _VarOp), _restrict! (each coarse cell writes itself), _prolong_add! (each fine cell writes itself; the eight weight products wi·wj·wk are hoisted out of the body and added in the old loop order: 1.59 ms instead of 2.20 ms at 128×128×64), and the fine operator of MG-CG (_apply_fine!, which writes out directly).
  • _l2 and _project_mean! use plane_partials! and ordered_sum, with the partials in a per-level buffer (MGLevel.part).

test/ka_multigrid.jl compares the smoother, residual, fine operator, restriction and prolongation with verbatim copies of the old loops, bit for bit. It covers even and odd nx, constant and cut-cell coefficients and three closures, on the default, the serial and a threshold = 1 backend (the last threads every launch).

Serial coarse levels. No multigrid-specific threshold: the coarse levels go through the global launch! threshold (32 768 points). A colour sweep covers half a level, so at 64×64×32 only the finest level is threaded (65 536 points per colour), and at 128×128×64 the two finest. 32×32×16 and below, and the 50 sweeps of the coarsest solve, run serially on the calling task. _restrict_coeff is setup only and stays a serial loop.

Projections. The operator is always singular (every axis periodic or Neumann), so the mean is projected out up to six times per level per cycle: after each smoothing, after the prolongation, from the residual and from the coarse right-hand side. Where it saves a sweep the projection is fused into a neighbouring kernel:

  • the residual's mean is subtracted inside the restriction, which reads r − m. The result has the bits of a projection followed by the restriction, and the sweep that wrote the projected r is gone;
  • the right-hand side's mean is reduced while it is copied in (fused plane_reduce!);
  • the final projection of the solution is fused with the copy-out;
  • the projection of the convergence check's residual is fused with its sum of squares.

The sums were not fused into the stencil launches. A plane_reduce! whose body evaluates the residual and writes it took 1.49 ms at 128×128×64 on one thread. The residual launch plus a separate sum took 0.90 ms: the eight-lane reduction keeps the stencil from vectorising. The restriction showed the same (0.24 against 0.10 ms).

KA-n: radiation and stochastic modules (#305)

Radiosity. Three changes.

  • LU cache. RadiosityFactorCache keeps the dense LU of $M = I - \mathrm{diag}(\rho) F$ between calls and refactorises only when $F$ (by identity) or $\rho$ (by value) changes. A hit runs the same LAPACK getrs on the same factors, so the bits equal a refactorisation at the same BLAS thread count. The radiosity_sun coupling keeps one cache per band. The longwave $\rho = 1 - \varepsilon$ is fixed, so its LU is computed once per run. The shortwave albedos follow μ₀ (default_urban_materials(; μ₀); all five classes change, from 0.140 / 0.268 / 0.293 / 0.359 / 0.272 at μ₀ = 0.1 to 0.121 / 0.204 / 0.186 / 0.031 / 0.217 at 0.9), so the shortwave operator is still refactorised on every daytime call.
  • BLAS. Pinned to one thread when Julia runs threaded (KA-a); the LU and its solves run on dense_blas_threads() since #496 (1.773 → 0.358 s for the 5639 facets with the threaded assembly, 12 threads). LAPACK rounds differently per BLAS thread count, within round-off.
  • View factors and aggregation. view_factors is one launch_weighted! over pairs of upper-triangle rows (p, n − p), each writing F[i, j] and F[j, i] of its own rows. The Gauss nodes are cached before the threads read them, and the occlusion quadrature no longer allocates. F and F_sky are bit-identical to the serial loop. aggregate_to_grid gathers through a CSR column → facets index (facet_column_index) in ascending facet order, which gives the same sums as the old facet scatter (bit-identical, no expectation change). An exact tie between dominant classes goes to the lowest material index. set_temperatures!(scene, Ts, facet_col) is one launch over the facets.

The iterative (Gauss-Seidel) radiosity solver stays serial.

Gas optics and two-stream. compute_optics! is one launch_weighted! over (column, layer): a work item fills one layer's g-points in the serial loop order, so the optics are bit-identical at every thread count. The k-distribution bisections are 33 of the 37 ms of a Berlin radiation call. The multi-column forms take optics τ[k, g, c] (allocate_column_optics). solve_sw! / solve_lw! launch over (g-point, column) work items, with the adding recurrence sequential in $k$ inside each item. Per-(g, column) scratch lives in a reusable TwoStreamWorkspace, so a call does not allocate. A second launch sums the g-points in ascending order. A single-column solve is the multi-column solve on one column (one code path), so column $c$ gets the single-column bits. column_radiation!, the entry the Berlin child and the nesting parent share (#259), runs through these forms.

Cloud shadow. The optical-depth field is a pointwise launch, and the slant rays are one launch_weighted! over the columns, one ray per work item. Both are identical to the old loops.

KA-j: the step cores (#306)

What the drivers do now. step! (_euler_projection!), step_rk3!, step_adaptive!, step_imex! and the sound-proof cores of Anelastic keep their serial operator order. Every operator they call is a kernel: the finite-volume operators of KA-d, the solvers of KA-g / KA-h, and the field algebra below.

  • One axpy. The three copies of _axpy_interior! (Simulations, TimeIntegration, Anelastic) are gone. Simulations.axpy!(y, a, x) is one interior_map!. _combine2/3/4! (the IMEX stage sums), p = φ/Δt (pressure_from_potential!) and the ν + K freezes of step_imex! are interior_map! / range_map! kernels with the expression of the broadcast they replace. The tendencies are zeroed with fill! and copies use copyto! (zero_storage!, copy_storage!): a memset / memcpy beat the pointwise kernel (see A reset is a memset below).
  • RK3. step_rk3! copies uⁿ into its workspace (copy_storage!) and forms the stage combinations ¾uⁿ + ¼u and ⅓uⁿ + ⅔u as kernels over the whole storage (combine_storage!; the in-place array is the first argument, so the loop vectorises: 0.56-0.68× the broadcast). Since SC-d (#404) the combination is written by the projection's correction pass and the scalar update, and on the halos by one halo-shell launch; combine_storage! is gone (see "SC-d" below).
  • Fused CFL sweep. cfl_diagnostics made five sweeps: the advective rate and one maximum each of νh, νv, κh, κv. It now makes one: a range_max whose body returns the 5-tuple, each component NaN-propagating (_cfl_maxima). N² comes from plane_mean!.
  • Fused step guard. After a step, step_adaptive! checked finiteness (one sweep per field), ran the divergence kernel, took its maximum, and took one maximum per velocity component. step_guard(sim) does all of it in one sweep: per point (Σ x·0, |∇·u|, max(|u|,|v|,|w|)) over u, v, w, θ, p (and qv). x·0 is 0 for a finite x and NaN for NaN or ±Inf, so the first component is 0 exactly when every value is finite. |∇·u| uses the divergence stencil _div_at of FiniteVolume, the one max_divergence uses. The verdict is the old one, in the old order: non-finite, then divergence, then the speed cap. The guard no longer writes the post-step divergence into div_buf.
  • Rollback. save_state! / restore_state! copy with copy_storage!, and restore_state! synchronizes the backend (Backends.synchronize, a no-op on the CPU) before the retry reads the state. The snapshot now holds νt and κt too (#346 item 1): before, a rejected try left the NaN coefficients of the blown-up state in sim.νt / sim.κt, where the diagnostics and a crash checkpoint read them.
  • _all_finite is IO.allfinite on the interiors, the one branch-free finiteness test (#346 item 2).
  • Per-simulation workspaces. The process-global WeakKeyDicts _SNAPSHOTS, _IMEX_WORKSPACES and _RK3_WORKSPACES are replaced by a StepWorkspaces field of each simulation (BoussinesqSimulation, MassWeightedSimulation). Each slot is allocated on first use with Backends.allocate. A lookup in a shared dictionary raced when two domains were stepped from different tasks; a field of the simulation does not. test/ka_step.jl steps two domains concurrently and compares them with the sequential bits.
  • Anelastic. weighted_divergence!, weighted_momentum_advect!, weighted_scalar_advect!, add_anelastic_buoyancy! and set_reference_state! are launch! bodies with the z-dependent weights as arguments indexed by k. max_*_divergence and the maxima of adaptive_dt use range_max / interior_max.
  • Open boundaries. The combination and restore of the open-boundary buffers in step_rk3! and the rollback are kernels.

Backends. range_max takes a tuple-valued body (several maxima in one sweep). range_map! substituted every argument that is out with a map returning a tuple of Unions, which made every interior_map! a dynamic dispatch allocating 128-256 B. ImmersedWalls now carries a face index built once by immersed_walls: compressed sparse rows face_ptr/face_entry, the faces in the order of their first pair, the pairs of a face in pair order. Each face sums its own pairs and updates its own velocity (owner computes), and the per-pair and per-face work vectors replace the work arrays and the per-call allocation of a. remove_stencil_wall_flux! subtracts each face's pair fluxes the same way. The diagnostics (F, τA, area, τ_min, F_stencil) are folded afterwards on the calling task, in the order of the former loops. fill_halos! stays outside the kernels.

No one-time change. The port plan named this gather as a one-time bit change. It is not one: a face's pairs are summed in pair order, which is the order the scatter added them in, so the gather gives the former bits. test/ka_hooks.jl compares every velocity, tendency and diagnostic with a transcript of the scatter (test/support/legacy_hooks.jl), also for a shuffled pair order. The kernels.

  • Immersed walls. The drag of every pair is a 1-D launch over the pairs. The face update is two 1-D launches over the faces: the faces with one pair (7 634 of 9 717 in the flagship) and those with several.   • IBM direct forcing. implicit_ibm_correction! and add_ibm_penalty! looped over the solid cells and scaled (or penalised) the six faces of each, so a face between two solid cells was written twice from two iterations. Now one work item per row (j, k) owns the row's u faces and the v and w faces on its cells' lower sides. It applies the operation of the solid cells in rows j − 1 and k − 1 to those faces first, then walks its own cells, one mask read per cell: per face the same operations in the same order as before. Rows with no solid cell in them or below them are skipped after word-wise scans of the BitArray. Walking each row face by face instead (up to six mask reads per face) measured 1.00× in an isolated call but 1.14× inside the flagship step (244 against 219 µs per call).   • Canopy drag. ResolvedCanopyDrag lists its faces with leaves once (act, u then v then w, each in k, j, i order).   • Moist buoyancy. The level sums were already a canonical plane_reduce! (KA-b). The deviation is one work item per level (a pointwise body that reloaded the level mean at every point cost 3.8×), and the w forcing is pointwise.
  • Large-scale forcing. KA-l: the SGS closures (#304)

Every subgrid closure's coefficient and memory update runs on launch!: the Smagorinsky family (static via KA-d; the dynamic procedure with plane, local and masked averaging; the Lagrangian scale-invariant and scale-dependent models), AMD (velocity and scalar), Vreman, the σ-model, the StabilityCorrected split with its N² / Rig / S² stencils, and the prognostic TKE and Reynolds-stress closures of PrognosticSGS. The point stencil `velocitygradientat/strainatstays the one shared@inline` function every body calls.

What runs how.

  • Pointwise bodies (bit-identical to the old loops): the Germano passes (pass 1 over the interior and one shell, |S|, pass 2 plain and masked), the local coefficient, ν_t, the masked velocities (one launch over the storage), the mask halo fill (one launch per direction and side), the box filter, the Lagrangian coefficient, power law, solid zeroing, cell velocity and pathline relaxation, AMD / Vreman / σ, the stability correction, N² / Ri / S², the TKE and RSM coefficients, the six RSM edge-stress placements, the TKE / RSM initialisations (a bisection per cell) and the storage-wide κ = ν/Prₜ, K = 2ν, κ_v = d κ_h broadcasts (range_map!).
  • Closures captured in kernels are gone. The _box_stencil_sum summands are named types (_GermanoAt, _GermanoFluidAt, _FluidCount, _ValAt, _MaskedValAt) summed in the fixed (dk, dj, di) order; the AMD buoyancy parameter of the sound-proof cores is the callable struct _LevelBuoyancy (the arithmetic of the closure it replaces). KA-m: column physics, one work item per column (#301)

Primitives (src/Backends.jl). foreach_column! runs a column body body!(i, j, args...) (or body!(n, args...) over a list of ids: the columns of one surface type, the facets of a scene) as one work item. The body loops over its own levels in its own order and writes only its own column. What the old loops accumulated across columns, the body returns; the launch stores it in row c of a partials matrix (column-major c), and column_sums folds each term in row order from zero. column_sum does both, and on the calling task it adds the terms as they come (no partials array). Both paths add the same numbers in the same order, so a total is identical at every thread count and equal to the old s += x loop. A maximum is foldl(max, …) over the partials (exact in any order). foreach_cell! is launch! with a weight, or plane_reduce! with per-plane partials. weight is the work of one column in grid points (its levels, or its root solves), so that the serial threshold counts the real work.

What runs per column.

  • Surface exchange (step_all_surfaces!): the columns are grouped by concrete surface type at init! and each group is one launch, so every launch calls step_surface! on one type. The worst storage error, the worst MSHF ratios and the MSHF time are per-column partials; the delivery loop (:surface_flux) returns evaporation and the solid-write flag.
  • The parent's tiled surface (step_parent_surface!): one work item per parent column, with the area sums of the tile fluxes as partials.
  • aq_chem: the deposition velocities (one surface-layer solve per column) and the emissions; Chemistry.apply_dry_deposition! returns what each column removed. apply_photochemistry! was already a per-cell plane_reduce! (KA-b).
  • RadiationFog.fog_adjust!: one plane per work item, with an early exit for a cell with ql ≤ 0 and qv < (1 − 10⁻⁸) q_s, where the adjustment returns exactly zero. dew_exchange! and the Berlin dew pass: one column each.
  • Kessler: conversion per cell; the spectrum sedimentation one column per work item, a raining column allocating its own col / Nr scratch (the old loop shared one pair through a captured closure); the legacy upwind one column per work item in ascending k. This is also the only 3-D use of p3_sediment!; the Berlin case has no 3-D P3 coupling.
  • WallModels dynamic roughness: the masked mean wind, the drag parts and the residual at every α of the scan and the root solve.
  • UrbanSurface facet scenes: the trial steps of the implicit step, the final column advance and the lagged step, one work item per facet. A scene that lists one facet object twice is refused (it would race).

What stays serial, and why. The facet scene's coupled longwave / node solve between the facet launches and the building energy balance are global linear systems: every unknown depends on every other, so there is no column to give a work item. The LU solve also depends on the BLAS thread count, which is why the harness section pins BLAS to one thread. Per-tracer parallelism is a follow-up.

Global caches. RadiationCore._gauss_legendre is the one source of Gauss-Legendre nodes; SurfaceOptics and Radiosity delegate to it (their copies were the same arithmetic and gave the same bits). Orders 1-64 are a table computed when the module loads; higher orders are memoised under a lock. The aerosol bulk-optics memo and the SNICAR table are locked (the SNICAR file is read once). The Mie log-derivative buffer was one global vector, and two tasks calling mie_sphere at once corrupted each other's recursion. The new first-use-under-threads test found this; the buffer is task-local now (2000 calls: 4.39 → 4.02 ms).

SC-a: roofline profile and thread pinning (#401)

Where the time of the flagship step and of the 256³ DNS step goes, kernel by kernel, against the machine's memory bandwidth, and whether pinning the threads helps. Script: benchmarks/bench_roofline.jl; the same machine as KA-o (Ryzen 9 7900: 12 cores in two CCDs of 6, 32 MB of L3 per CCD, 24 hardware threads; dual-channel DDR5), Julia 1.13.1, master of 2026-10-08. Most runs were taken on the branch point before #400 and #392 merged; neither changed src/, and the Berlin example changed only in the dt check of #392, which step_case!(case) does not take. The dns_step! row, whose history #400 rewrote, was re-measured after the merge (its step_rk3! came out within 3 % of the earlier runs). Every run started with the 1-minute load below 4 and at least 12 GB free; every figure is the minimum over three or four processes.

How it is measured. The script replaces Backends' three launch paths (_launch!, _plane_partials!, _serial_column_sum) by copies that time each call and book it under the kernel body's name, so every launch of the step is seen, with no change to src/. Per kernel it records calls per step, whether they ran serially (below the backend's threshold), µs per call, and the compulsory bytes: every distinct numeric array the body reaches, counted once, capped at the launch's points. That is a lower bound on the traffic (an axpy counts 2 arrays where STREAM's triad counts 3). In the same process it measures STREAM copy and triad on 256 MB arrays (DRAM) and on 8 MB arrays (L3), and the empty threaded launch. Launches over 10⁶ points (the nest parent's 192 × 192 × 53 fields, the DNS) are booked apart, as [≥1M]. The profiled step runs 0-15 % above the plain step even with the profiler's own time taken out (it evicts cache), so the step times below are those of plain runs (ROOFLINE_PROF=0) and the in-launch times those of profiled runs.

Classes. Serial: ran below the threshold. Bandwidth: its bytes at the DRAM triad bandwidth take at least half its time, so only moving fewer bytes helps. Compute: its one-thread time over 12 threads takes at least half. Overhead: neither, so launch, synchronisation or imbalance dominates. "Excess" is the time per call that neither bound explains. The roof is DRAM for the 64³ child too: its fields would fit in L3, but between two uses of a field the step touches more than L3 holds, and its threaded launches move their compulsory bytes at 53 GB/s in all (1.32 GB in 24.8 ms per step), 1.35× the DRAM triad and 9 % of the L3 triad (573-587 GB/s).

SC-b: threaded halo fills (#402)

KA-o measured fill_halos! at 1.0× on 12 threads at 64 × 64 × 32: every per-axis phase of a fill (halo_kernels.jl) is a separate launch, and at the flagship's sizes each face slab is below the backend's 32 768-point threshold, so the fills ran serially between threaded stencils.

Decomposition. The phases cannot run at once (an edge or corner holds the value of the last axis that reaches it), but every x and y phase reads and writes one k-plane only (the open-boundary plane buffers are read at the same (j, k)) and every z phase one (i, j) column only. A fill is therefore two launches: (1) each work item takes a contiguous chunk of k-planes of every field and runs that field's x then y phases restricted to them; (2) each work item takes a chunk of j-rows and runs the z phases. The restriction is carried by the array (_Clip, halo_sets.jl): the fill methods of every BC type run unchanged on it and its _halo_launch! narrows the phase to the clip's planes or rows, serially in launch!'s order. Every point is computed from the same operands in the same order as the unrestricted fill, so the bits are the same at every thread count and every chunking, including the N < H phases whose layers depend on each other.

Sets. fill_halos!(fields::Tuple, bcs) (one bcs or one per field, plus the per-field open-boundary keys) and fill_halos!(fields::AbstractVector, bcs) fill a whole set in the same two launches, weighted by the halo points of the set. The call sites that fill several fields together now do it as one set: the prognostic state in the step cores (fill_state_halos!), the velocities before the projection, the CFL diagnostics and the step guard, the anelastic step, the advected tracers, the turbulence diagnostics, the nest's interpolated state and the DiffusivityTensor components. A single-field fill_halos!(f, bcs) is a set of one. Below the threshold and at one thread the set is the historical field-by-field, phase-by-phase fill.

Tests. test/ka_halos.jl checks the set fill (θ, u, v, w as one tuple, and a vector of three tracers sharing one set of conditions) against the pre-port loops for every closed and open BC case of the KA-f tests (23 on the two larger meshes, 10 on the N < H mesh), at 1, 2, 5 and more-chunks-than-planes work items and through the public method on the serial, default and zero-threshold backends; the thread-invariance worker hashes set fills (periodic, walls, open) at every thread count. What is left is the traffic between kernels. Of SC-d's "not fused" list only one pair has nothing global between its two halves: the tendencies and the predictor u ← u + Δt·tu (the divergence needs the halo fill of u*, the correction the FFT solve). The sweep (FiniteVolume.blocked_predictor!). The k-range is cut into one slab per thread. A slab is swept j-row by j-row: the tendencies of row j (every k of the slab) go into a ring of two rows (SweepBuffers, 2 × 5 × 22 × 262 values per slab at 256³, in L2), then row j − 1 gets its predictor in place, since no later tendency of the slab reads it (the stencils reach j ± 1, k ± 1). A slab's first and last planes are read by the neighbouring slabs, so their tendencies are kept (edge) and updated in a second launch once every slab is done. Every value is the expression of the separate passes (_tend_u … then the predictor functor), so the bits are the same for any slab count and thread count, and the same as the unblocked core: test/ka_blocking.jl checks 1-5 slabs, regular and stretched grids, dry and moist, step! and step_rk3! against the separate passes and against the pre-fusion cores of test/support/legacy_fusion.jl. The tendency fields are neither read nor written on this path; the halo zeroing of the tendencies goes too.

It applies when nothing adds to the tendencies or reads the state between the base tendencies and the predictor (_blocked_core): the built-in momentum advection and no SGS closure, buoyancy, Coriolis, surface flux, sponge, body_force!/post_predictor! hook or open boundary, on the CPU. That is the DNS core. θ (and qv) are updated in the same sweep, before the projection, which does not read them. The flagship child and parent have SGS, buoyancy and hooks, so they keep the SC-d path: SC-e does not change the flagship.
