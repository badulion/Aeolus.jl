Logging

Aeolus.RunLog is the logging core of the library (LOG-a, #333; the full design is epic #293). The rule is simple: the library emits structured events and never prints; the caller decides what is shown and where by installing a logger. Events go through the standard library's Logging (@debug, @info, @warn, @error), so any AbstractLogger works, and there is no dependency beyond the standard library.

Running with a run log

using Aeolus

with_run_log("runs/my_case/run.log") do       # info → console, debug → run.log
    for n in 1:nsteps
        step_adaptive!(sim, cfl)
        maybe_checkpoint!(ck, sim; step = n)
    end
end

The console shows info and up with HH:MM:SS.sss timestamps; run.log gets debug and up with full timestamps and the source location of every record. AEOLUS_LOG=debug (or info, warn, error, off) overrides the console level. The file is appended to, so a restart continues the same log; an error that ends the run is logged at Error level, with its backtrace, before it propagates. Without with_run_log, open the logger yourself and close it at the end:

lg = open_run_log("run.log"; console = stderr, console_level = Logging.Info,
                  file_level = Logging.Debug)
with_logger(lg) do … end
close(lg)

Flush policy

run.log is not flushed after every record (maintainer decision of 2026-10-06, PR #346):

recordon disk
Warn, Errorat once (and everything buffered before it with it)
Debug, Infoat the next record more than flush_interval seconds (default 5) after the last flush
anything still bufferedat close: the end of with_run_log or with_run, also when the run throws; and by an atexit hook if the process dies of an uncaught error with the log still open

So only a hard kill (SIGKILL, the OOM killer, power loss) can lose the last few seconds of debug and info lines; a warning or error never waits in a buffer. There is no timer task: the clock is read when a record arrives, which keeps logging deterministic and thread-free, so a debug line written just before a long quiet spell stays buffered until the next record or the close. To follow a run with tail -f run.log at record granularity, or when debugging a hang, use flush_interval = 0 (flush every record, the LOG-a behaviour):

with_run_log("run.log"; flush_interval = 0) do … end
lg = open_run_log("run.log"; flush_interval = 1.0)   # or any interval
flush(lg)                                            # force one now

The keyword is AeolusLogger's (flush_interval = 5.0); open_run_log passes it to the file. The console logger and the test logger flush every record.

A run log line:

2026-10-06T17:26:07.029 WARN  pressure[child] MultigridPoissonSolver: maxcycles=50 reached, rel. residual 2.1e-5  cycles=50 relative_residual=2.1e-5 tol=1.0e-8  @ Multigrid.jl:687

Event conventions

Every event of the library carries two tags:

keymeaning
subsystemthe emitting part of the code, a Symbol
domainthe domain of a multi-domain run, current_domain(): :main unless a driver wraps the step in with_domain

and its numbers as further key-values, so a test or a diagnostics sink reads them without parsing text. A new event follows the same pattern:

@warn("MySolver did not converge", subsystem = :pressure, domain = current_domain(),
      iterations = it, relative_residual = rel, tol = s.tol)

Key-values are evaluated only when some logger wants the record, so a disabled @debug costs a level check (under 1 µs, asserted in test/logging_core.jl).

The events the core emits today:

subsystemleveleventkey-values
:pressureWarnCGPoissonSolver hit maxit / breakdownsolver = :cg, iterations, residual, relative_residual, tol; for a breakdown reason = :breakdown, curvature
:pressureWarnMultigridPoissonSolver hit maxcyclessolver = :multigrid, cycles, relative_residual, tol
:pressureWarnDensityWeightedPoissonSolver breakdown / no convergencesolver = :density_weighted_cg, reason = :breakdown | :maxit, iterations, curvature or residual, relative_residual, tol
:diffusionWarnsolve_implicit_diffusion! breakdown / maxit (when warn = true)reason, iterations, curvature or relative_residual, tol
:timesteppingDebugstep_adaptive!: the stepper threw (recovered by a retry)dt, retry, exception
:timesteppingDebugstep_adaptive!: retry at a smaller stepreason, from, to, retry, max_retries
:timesteppingWarnstep_adaptive!: a fast process left non-finite valuesdt, processes
:checkpointWarnrestart! across Julia versions / with allow_mismatchpath, written_by, running / parameters
:checkpointDebugresume!: fresh start / resumedevent = :fresh_start | :resume, dir / path, t, step
:checkpointDebugmaybe_checkpoint! wrote a checkpointevent = :write, path, step, t, removed

So a healthy run emits nothing at Info or above: the default console stays quiet, and run.log records the retries and checkpoints. Under a NullLogger nothing reaches stdout or stderr at all.

One switch: the logger level

There are no verbose keywords (removed outright by #347, maintainer decision of 2026-10-06, without a deprecation): what is shown is decided only by the logger the caller installs and its level. The library, the examples and the test fixtures follow one convention:

levelforexamples
Debugchatter: what a run log should keep but a console need not showadaptive-step retries, checkpoint fresh start / resume / write, a costly diagnostics row, the Berlin setup summary
Infomilestonesthe run header, the progress line, the Berlin output frames (with each coupling's diagnostics) and end-of-run events (stage timing, ledgers)
Warnproblems the run survivesa solver that did not converge, a non-finite fast process, a restart across Julia versions
Errorthe run stopsa blowup, an error that ends with_run

To see the retries on the console, raise the console level instead of passing a keyword:

with_run_log("run.log"; console_level = Logging.Debug) do … end   # or AEOLUS_LOG=debug
with_logger(NullLogger()) do … end                                # silence everything

Run folder and provenance

A production run writes one folder (#334), runs/<yyyy-mm-dd>_<case>_<runID>/:

filecontents
run.logthe run log: debug and up, full timestamps, source locations; appended to by every session
run.tomlprovenance: run_id, case, created, the full config and seeds, one [[session]] per start or restart; for a RunConfig the canonical [config], config_hash, config_sources, [inputs] hashes and replayable
diagnostics.csvthe scalar diagnostics time series (diagnostics_path; written by the run monitor)
diagnostics.ncthe same rows plus the vertical profiles, NetCDF-4, with the provenance as global attributes (diagnostics_nc_path; see diagnostics.nc)
crash/crash checkpoints of a blown-up run (crash_dir; see Blowup)
output/the run's output files (output_dir)
checkpoints/the CheckpointSchedule and FFTW wisdom (run_checkpoints)
uncommitted-<n>.diff, untracked-<n>.txtthe uncommitted code of session n, only with allow_uncommitted = true

run.toml [config] is the configuration of record. For a run started from a RunConfig (every aeolus run, every shipped config), [config] is the canonical resolved TOML: every option written out (every domain's sections under [[domain]]), paths absolute, floats bit-exact. It is what load_run_config(folder) reads, what aeolus run <folder>/run.toml replays and what aeolus run <folder> --resume continues; the free-form config of a run started from a Dict or a struct is kept for provenance only and cannot be replayed. See Run configuration.

using Aeolus

with_run("gabls1"; config = cfg, seeds = (; noise = 42)) do rf
    ck  = run_checkpoints(rf; every_steps = 500)      # before the simulation: loads the wisdom
    sim = build_simulation(cfg)
    resume!(ck, sim)                                   # continues from the folder's newest checkpoint
    for n in ck.last_step+1:nsteps
        step_adaptive!(sim, cfl)
        maybe_checkpoint!(ck, sim; step = n)
    end
end

with_run calls start_run, installs the run log as the current logger while f(rf) runs, and finish_run! at the end. If f throws, the error and its backtrace go to run.log, the session is recorded as failed (or interrupted) with the message, and the error propagates.

Restart. with_run(case; resume = folder) (or resume = :latest, the newest folder of case under root) reuses the folder: the run ID stays, run.log is appended to, and run.toml gets a new session of kind "restart". A restart whose config, seeds or git commit differ from the first session logs a warning and records the new values in its session; a previous session that never finished (no end time) is marked aborted.

Uncommitted code is blocked. Before anything is written, start_run checks the git work tree of the Aeolus sources (repo): staged, unstaged or untracked changes throw UncommittedCodeError, listing the files. allow_uncommitted = true (or AEOLUS_ALLOW_UNCOMMITTED=1) runs anyway, saves git diff HEAD and the untracked file list in the folder, and logs a warning. Ignored files and the run folders themselves do not count (runs/ is in .gitignore). Code that is not in a git work tree (an installed release) starts, with git.available = false in the record. Only start_run looks at git: tests and in-memory runs are unaffected.

What a session records (provenance):

tablekeys
(session)number, kind, started, ended, status, wall_seconds, allow_uncommitted, error
gitavailable, repo, commit, branch, dirty, changes, diff_file, untracked_file
juliaversion, commit
aeolusversion, source
manifestpath, fnv1a64 (FNV-1a 64-bit hash of the Manifest bytes)
packagesevery package in the Manifest with its version
hosthostname, os, arch, cpu, cpu_threads, julia_threads, blas_threads
commandjulia (the Julia command), program, args, cwd
fftwplanner, threads, wisdom_loaded, wisdom_file, bitwise_reproducible (refreshed by run_checkpoints and at the end)
envevery AEOLUS_* environment variable

The log header carries the same: one Info record (subsystem = :run, event = :start or :restart) with the run ID, folder, commit, versions, host, threads and FFTW policy, shown on the console, and one Debug record with the whole session record and the config, kept in run.log only:

18:02:11.374 INFO  run[main] run started  event=start run_id=e072ceb3 case=gabls1 folder=…/runs/2026-10-06_gabls1_e072ceb3 session=1 commit=d08c8d30a5c0 branch=master julia=1.13.1 aeolus=0.0.1 manifest=8595c875cf129a87 host=geralt threads=1 fftw_planner=measure fftw_threads=1 wisdom_loaded=false bitwise_reproducible=false

The run ID comes from the operating system's entropy source, so starting a run does not advance the global random number generator.

Cost. start_run + finish_run! take 11.6 ms per run (git calls, provenance, run.toml, the header; 64×64×32 benchmark below). Nothing is done per step: on the 64×64×32 Boussinesq case (step_adaptive!, one thread, benchmarks/bench_run_folder.jl) a step took 13.37 ms with a NullLogger, 13.17 ms inside with_run and 13.20 ms inside with_run with one six-key @debug record per step, medians of 9 interleaved repetitions on a loaded machine whose repetition spread (11.8 to 14.7 ms) is far larger than the differences.

Diagnostics registry

One generic, diagnostics(component, sim), declares the scalar diagnostics of anything that runs in a simulation (#335). Each is a Diagnostic: a name, its units, a cadence class (:step, cheap, every record; :costly, on the writer's cadence, default every 60 s simulated) and a reduction (:max, :min, :maxabs, :sum, :mean, :rms, or :value when the source already returns the scalar), with a source function. The reduction is declared rather than done by the source, so the threaded, deterministic reductions of the KernelAbstractions port replace reduce_diagnostic without touching a component (#336).

# a component of your own
Aeolus.RunLog.diagnostics(c::MyTracer, sim) = [
    Diagnostic("mass", "kg", () -> tracer_mass(c, sim)),                        # :value, :costly
    Diagnostic("c_max", "kg m-3", () -> interior_view(c.field); reduction = :max),
    Diagnostic("source_rate", "kg s-1", () -> c.rate; cadence = :step),
]

ds = collect_diagnostics(sim, (; sgs = closure, wall = wm, tracer = c))
# ke_mean, max_abs_u, …, sgs.nu_h_max, …, wall.ustar_mean, …, tracer.mass, …

collect_diagnostics takes the simulation's own and prefixes each component's with its key; a name declared twice is an error. A source that throws gives NaN and one warning, so a broken diagnostic never stops a run. What the library declares (each source calls the component's own function, one source of truth):

componentdiagnostics (:costly unless marked)
BoussinesqSimulationke_mean (kinetic_energy / domain volume, m² s⁻²), max_abs_u, max_abs_v, max_abs_w, theta_min, theta_max, max_div (max_divergence), nu_t_max, qv_max (with moisture)
MassWeightedSimulationke (density-weighted, J), max_abs_u/v/w, theta_min/max, max_div (the core's own constraint: anelastic or pseudo-incompressible residual, s⁻¹)
any AbstractSGSClosurenu_h_max, nu_v_max, kappa_h_max (via sgs_fields); TKEClosure adds e_mean, e_max
WallModelustar_mean, ustar_max of the bottom wall (the law at the first-cell speed, from apply_wall_stress! with a zero step)
TBLEWallModelper wall used: <wall>.utau_mean (its active columns), <wall>.kappa_wm
WallBoundedCase (the test fixture test/fixtures/channel_cases.jl)tau_wall_bottom, tau_wall_top, with a scalar q_wall_bottom, q_wall_top (all :step); a TBLE wall model's under wall.
NestedRunparent_steps, child_substeps, parent_retries, child_retries, substeps_last, max_child_cfl, max_clock_error (:step); the stage wall times; every diagnostic of both domains under parent. and child.

The Berlin case (an example, not the library) implements the same generic for each of its couplings, diagnostics(c, case), and adds its frame quantities, ledgers and stage timing; the berlin run driver hands them to the run monitor (#338, the Berlin case). Its wall-clock quantities are all named wall.….

Profiles

Vertical profiles are declared the same way (#337), through profile_diagnostics(component, sim), each a ProfileDiagnostic: a name, units, the name and heights of its vertical axis, and a source that returns the profile (the source does the horizontal reduction, through the port's deterministic plane_mean! or the core's own profile functions). collect_profiles prefixes them as collect_diagnostics does, the axis included (parent.z, child.z). They are evaluated on the costly cadence and go to diagnostics.nc only.

componentprofiles
BoussinesqSimulationon z (cell centres): u, v, theta, qv (with moisture): horizontal means; w_theta, the resolved ⟨w'θ'⟩ (resolved_flux_wθ); on zf (w faces): w_var (horizontal_variance)
MassWeightedSimulationu, v, theta on z, w_var on zf
any AbstractSGSClosurenu_v, the mean vertical eddy viscosity (via sgs_fields); TKEClosure adds e
NestedRunboth domains' profiles under parent. and child., on their own axes

diagnostics.csv

A DiagnosticsWriter appends one row per record_diagnostics!:

step [1],t [s],wall [s],dt [s],dt_limiter,retries [1],ke_mean [m2 s-2],max_abs_u [m s-1],…
1,5.0,6.879,5.0,advective,0,0.5352798106352713,1.8665482844936574,…
2,10.0,7.458,5.0,advective,0,,,…

The costly cells are empty between their evaluations. Numbers are Julia's shortest round-trip form, so a cell read back is the Float64 that was computed (tested bit for bit); a non-finite value is NaN, Inf or -Inf. A restart appends below the same header; a file whose columns differ is left alone and the session writes diagnostics-2.csv with a warning. Each costly row is also a Debug record (subsystem = :diagnostics) in run.log.

diagnostics.nc

A DiagnosticsNCWriter writes the same rows as NetCDF-4 (#337, through NCIO: deflate, shuffle, CF attributes), plus the profiles. The file has two unlimited dimensions, so no costly quantity is padded with fill values between its evaluations:

dimensions:
    time = UNLIMITED ;          // one record per row of diagnostics.csv
    time_costly = UNLIMITED ;   // one record per costly row
    z = 32 ; zf = 32 ;          // profile axes; equal levels share one
variables:
    double time(time) ; int64 step(time) ; double wall(time) ; double dt(time) ;
    string dt_limiter(time) ; int retries(time) ;      // + every :step scalar
    double time_costly(time_costly) ; int64 step_costly(time_costly) ;
    double ke_mean(time_costly) ; double max_abs_w(time_costly) ; …  // every :costly scalar
    double theta(time_costly, z) ; double w_var(time_costly, zf) ; …  // every profile

(ncdump order; in Julia ds["theta"] is (z, time_costly).) Every variable has units and long_name, a reduced scalar its CF cell_methods (area: maximum, …). Time is in seconds of simulated time; time_origin = DateTime(…) gives it CF units seconds since …, so xarray and NCDatasets decode dates.

Provenance. In a run folder the global attributes are nc_provenance_attributes of the session: run_id, case, session, git_commit, git_branch, git_dirty, julia_version, aeolus_version, manifest_fnv1a64, hostname, julia_threads, blas_threads, fftw_planner, fftw_threads, fftw_wisdom_loaded, bitwise_reproducible, command, config and seeds (the session's configuration and seeds as TOML, with config_hash for a RunConfig), created (the run), session_started and session_finished (set when the writer closes; empty while the session runs or if it died), plus title, source and a history line per session. Flags are Int8 0/1 (NetCDF has no boolean). run.toml stays the full record (every session, every package version).

Restart. A restart appends to the file when its layout (variables, units, cadence classes, profile levels; stored in the attribute aeolus_diagnostics_layout) is the same, refreshes the attributes to the new session and adds a history line; otherwise the session writes diagnostics-2.nc, as the CSV does. The costly cadence restarts with the session (its first row is costly).

Flushing. The rows of time are buffered and written as one block at the first row 5 s wall after the last write (flush_interval, the run.log policy), after 1000 rows, when a blowup is thrown out of the monitor, and on close; each write ends with an HDF5 sync, so after a crash the file holds every written row. A sync costs about 2 ms, which is why the rows are not written one by one. The costly rows (scalars and profiles, evaluated when due) are buffered with them and written in the same block (#514): written at once, a costly row cost 13.5 ms, of which the five profiles are 0.085 ms.

Progress line

A ProgressLine(t_end) emits, at most every every wall seconds (default 10), one Info record (subsystem = :progress), so it reaches the console and run.log:

18:37:00.311 INFO  progress[main] t = 25.1 s (12.5 %)  719.9 steps/s  ETA 0:00:52  dt = 0.823 s (advective)  last warning (0:00:12 ago): MultigridPoissonSolver: maxcycles=50 reached …

with the key-values t, percent, step, steps_per_s (over the last interval), eta_s (the simulated time per wall second since the start, extrapolated), dt, limiter and last_warning. The last warning is noted by a WarningTap around the current logger (with_progress, or the run monitor). The binding limit of dt comes from the caller until the step cores report it (#336).

Blowup: diagnose, dump, stop

A BlowupGuard checks the state for NaN and Inf every every_steps steps (default 10) and keeps the last state that passed as an in-memory checkpoint_payload (fields with halos, closure memory, components, stepper, RNG). When the run blows up, a non-finite value at a check (check_blowup!) or a step that throws (guarded_step!, e.g. step_adaptive! out of retries), it

  1. diagnoses: one Error record (subsystem = :blowup, event = :blowup) with the step, the time, the cause, and, per non-finite field (nonfinite_fields), the count and the index and coordinates of the first bad value, then the last value of every diagnostic:

    18:37:00.649 ERROR blowup[main] blowup at step 26, t = 33.587 s: non-finite values in θ; crash checkpoint of step 21 written  …
    │ details =
    │   θ: 1 of 4096 non-finite (1 NaN, 0 Inf), first at (7, 7, 7) = (325.0, 325.0, 162.5) m
    │   last ke_mean = 5.670237360521602 m2 s-2  (step 14, t = 25.09735475430639 s)
    │   …

  2. dumps the crash checkpoint crash/crash_<step>.jls of the last good state: the current state when it is still finite (a throwing step_adaptive! restores the start of its step), else the state of the last passing check (under an attached monitor stepping with step_adaptive!, the state at the start of the checked step, see below). It is an ordinary checkpoint: restart! continues from it (tested bit for bit);

  3. stops with a BlowupError carrying all of it. Inside with_run, the session is recorded as failed.

The check covers the state the checkpoint components hold outside the simulation too (component_nonfinite_fields): in a nested model the guard steps the root's core, and the nest reports its child domains, each field named <domain>.<field> (inner.θ). A one-way child feeds nothing back, so without this a NaN in it never reached the root and the run ended completed (test/model_nesting.jl).

Only BoussinesqSimulation has a checkpoint format (#245) today; for the other cores the diagnosis is logged and says that no checkpoint was written.

What a check costs (#514). A check is one fused, threaded sweep over every inspected field (interior_allfinite) and a copy of them. Between checks the guard reads one interior value of the pressure: the solve spreads a non-finite value anywhere over the whole field, so a fixed-step run is stopped at the step a velocity blowup reaches the solve, not at the next check. Under an attached monitor whose simulation steps with step_adaptive!, a check repeats nothing the step has done itself: the step's post-step guard has swept u, v, w, p, θ (and a moist core's qv; guard_covered), so the check sweeps only νt, κt (and a dry core's qv), and it keeps the step's rollback snapshot, the state at the start of the checked step, as the last good state instead of copying the state (the simulation gets the buffers of an older kept snapshot; two are kept and swept only if a blowup needs them). The rest of that crash payload (closure memory, components, stepper, RNG) is taken when the step starts (step_begun). The blowups caught are the same, at the same step (scenarios against master in PR #514): νt, κt, qv and every prognostic field, a non-finite fast process, a throwing step, not attached and attached; the crash checkpoint is one step older; fixed-step runs are stopped earlier.

Run monitor

RunMonitor puts the three behind one call per step. Given a run folder it writes the folder's diagnostics.csv, diagnostics.nc and crash/; each scalar is evaluated once per row for both files. with_monitor attaches it to the simulation by default (#336): it becomes the simulation's diagnostics hook, so the step cores report every step themselves and the driver only steps:

with_run("cbl"; config = cfg) do rf
    with_monitor(sim; run = rf, t_end = 4 * 3600.0, components = (; sgs = closure, wall = wm),
                 sgs = closure, stepper = st) do m
        dt = nothing
        for n in 1:nsteps
            _, dt, _ = monitored_step!(m, sim; step = n) do   # or just step_adaptive!(…)
                step_adaptive!(sim, cfl; dt_prev = dt, sgs = closure)
            end
        end
    end
end

monitored_step! is then only needed to turn a step that throws into a diagnosed blowup; the row came from the hook. Rows are numbered step0 + 1, step0 + 2, … (step0 keyword: the step a resumed run continues from). A driver whose step is several core steps, or which numbers its own steps (a run that resumes inside the driver), passes attach = false and calls monitor! after its step: the row then covers every core step since the previous row, with dt the time they covered, the last limiter and the summed retries (the SBL and Berlin drivers do; the bare-simulation and DNS drivers are attached).

Per-step diagnostics in the step cores

Every step core (step!, step_rk3!, step_imex!, step_adaptive!, the sound-proof cores, and per domain inside step_nested!) records its step in the simulation's StepRecord and then calls the simulation's hook (set_step_hook!; an attached monitor's MonitorHook). A core called inside another is part of the outer step (step! inside step_adaptive!), a rejected attempt is not a step, a step that throws records nothing. What each step costs to record is a few time_ns() calls and additions: nothing is swept for it.

Deterministic reductions. A Diagnostic source that returns a Field is reduced over the interior with the KernelAbstractions port's reductions: range_max for :max, :min, :maxabs (exact, the bits of a serial maximum), the canonical plane sums for :sum, :mean, :rms (the same bits at any thread count). The core and closure diagnostics return their Fields.

Why not a CFL sweep every step. On the 64×64×32 case below a fixed step! takes 5.3 ms; the advective-rate sweep 0.085 ms (1.6 %) and the fused sweep with the SGS maxima 0.15 ms (2.8 %): either alone would exceed the 2 % budget. So the every-row CFL numbers are those of the pick the step already made, and a fixed-step run gets its CFL on the costly cadence (cfl_*_state).

Cost (benchmarks/bench_run_monitor.jl, 64×64×32 Boussinesq, step_adaptive!, one thread, 15 interleaved repetitions of 40 steps, mean dt 0.14 s): 8.56 ms per step without a monitor, 8.70 ms with monitor! after every step at the defaults (costly row every 60 s simulated, progress line every 10 s wall, check and snapshot every 10 steps): +1.6 % (median of the paired ratios), within the 2 % budget of epic #293, but the repetitions of the bare step spread over 8.31 to 9.93 ms. Timed alone, the parts are a cheap row 0.6 µs, a costly row (the 8 core diagnostics) 1.46 ms, a blowup check 0.12 ms (a branch-free vectorised finiteness test) and a snapshot 0.26 ms (the field copies reuse the previous snapshot's buffers), which at the default cadence add up to 0.042 ms per step, 0.49 %; the benchmark fails if that exceeds 2 %. The worst case, costly diagnostics, check and snapshot after every step, costs +30 %.

With diagnostics.nc (#337; same benchmark, a later day, 7.18 ms per bare step, mean dt 0.10 s): the CSV-only monitor +1.40 %, the monitor with diagnostics.nc +1.55 % (paired medians; the bare-step repetitions spread over 6.99 to 7.38 ms). Its parts: a buffered row 0.2 µs, a block write plus sync 2.13 ms (once per 5 s wall), a costly row 6.5 ms (0.26 ms of it the five profiles, the rest the write and the sync; once per 60 s simulated). At the default cadence all parts add up to 0.060 ms per step, 0.84 %. The worst case (everything every step) is +137 %, dominated by the per-step HDF5 sync of the costly row. A first version synced every 20 rows: 146 µs per step amortised, 3.1 % from the parts, over budget; hence the wall-time flush.

With the step record and the attached monitor (#336; same benchmark, 32 steps × 15 repetitions so that the case stays below the ~2930 steps after which it blows up, on master too; a shared machine at 1-minute load 8 to 9, 5.38 ms per bare step, mean dt 0.10 s): the record's bracket around a step with a no-op hook costs 45 ns (0.001 %); a cheap row with the step-record columns 2.0 µs (0.6 µs before), a costly row 0.46 ms (the core, step-record and process diagnostics, with the port's Field reductions), a blowup check 0.13 ms, a snapshot 0.36 ms; diagnostics.nc's block write and sync 5.5 ms and its costly row 15 ms (both slower than the #337 figures, I/O under that load). At the default cadence the parts add up to 0.084 ms per step, 1.56 % of a step, within the asserted 2 %. The whole-step comparison is within the run-to-run noise at that load: the attached monitor +3.05 % and the driver-called one +5.63 % (paired medians) in one run, +4.03 % and +1.00 % in the run before (the bare-step repetitions spread over 5.26 to 5.61 ms).

By 2026-11-06 the same parts were 2.27 % of a 3.71 ms step: the step had become 30 % faster, the monitor had not, and the benchmark failed. After #514 (the attached check reuses the step's own guard and snapshot, the sweeps are fused and threaded, the costly rows are buffered): the default (attached) monitor's parts are 0.57 % of a step on one thread and 0.46 to 0.55 % on 4 and 8; a due check costs 0.068 ms (0.035 to 0.044 ms threaded) against 0.44 ms for the full check and copy; the monitor! path, which still copies, 1.4 to 1.6 %. The benchmark now also times every step on its own (null and attached interleaved, trimmed means): +1.1 to +1.5 % on one thread (master +2.8 to +3.1 %), about 2.5 times the parts, because a due sweep reads fields the step has pushed out of the cache and a per-step diagnostic read right after a step costs 1 to 5 µs instead of 0.1 µs. On 4 threads that measurement scattered from −1.2 to +4.6 % over five runs (master +2.9 to +6.4 %); the parts do not scatter, so they stay the asserted figure.

Cost of a record

Measured on a 64×64×32 Boussinesq case, step_adaptive!, one thread (#333): 9.14 ms per step with a NullLogger, 9.11 ms with the run log installed and no records (the difference is within the ±1.7 % run-to-run spread), 9.16 ms with one six-key @debug record per step written to run.log. One record costs 10.6 µs (0.12 % of the step), about half of which is the standard library's macro.

The flush policy (PR #346) measured on one machine, one thread, the same six-key @debug record to run.log, best of 7 × 20 000 records, three runs each: flushing every record (the old code, and flush_interval = 0) costs 8.82–8.98 µs a record, the default flush_interval = 5 7.89–7.98 µs, so the policy saves about 1 µs a record (11 %). Timed alone, format_record is 2.5 µs, write + flush of one line 0.68 µs against 0.05 µs for write alone, and the time() call the policy adds 23 ns. (The #333 figure of 10.6 µs was measured on a different day; the comparison here is like for like.)

Aeolus.RunLog — Module
Aeolus.RunLog

Structured logging for Aeolus (LOG-a, #333; design in epic #293).

The library emits events through stdlib Logging (@debug, @info, @warn, @error) with key-value pairs and never prints. Every event of the library carries two tags:

  • subsystem: a Symbol naming the emitting part of the code (:pressure, :timestepping, :diffusion, :checkpoint, …);
  • domain: the domain of a multi-domain run the event belongs to, current_domain() (:main outside with_domain).

What is shown, and where, is the caller's choice: they install a logger. This module provides the loggers a run needs, with no dependency beyond the standard library: AeolusLogger (one formatted, timestamped line per record), TeeLogger (several sinks, each with its own level), open_run_log / with_run_log (info and up to the console, debug and up to run.log) and test_logger (the test suite's: warnings and up, or the level of AEOLUS_LOG).

Aeolus.RunLog.AeolusLogger — Type
AeolusLogger(stream = nothing; min_level = Info, timestamps = :datetime,
             source = false, flush = true, flush_interval = 5.0, owns_stream = false)

A logger that writes one line per record:

2026-10-06T14:03:12.481 WARN  pressure[main] MultigridPoissonSolver did not converge  cycles=50 residual=2.1e-5 tol=1.0e-8  @ Multigrid.jl:685
  • stream: an IO, or nothing for whatever stderr is when the record is written (so redirect_stderr captures it).
  • min_level: records below it are dropped before their message or key-values are evaluated.
  • timestamps: :datetime (local yyyy-mm-ddTHH:MM:SS.sss), :time (HH:MM:SS.sss) or :none.
  • source: append @ file:line to every record; warnings and errors always carry it.
  • flush and flush_interval (seconds): the flush policy (maintainer decision of 2026-10-06, PR #346). With flush = true a record at Warn or above is flushed at once; a Debug or Info record is flushed only when more than flush_interval seconds have passed since the last flush. Anything still buffered is flushed by close(logger), which with_run_log and with_run call on every exit, including an error, and by an atexit hook if the process exits with the logger still open. So only a hard kill (SIGKILL, power loss) can lose the last few seconds of debug and info lines. There is no timer task: the clock is read when a record arrives, so a debug line written just before a long quiet spell stays buffered until the next record or the close. flush_interval = 0 flushes every record (the LOG-a behaviour); flush = false never flushes before close.
  • owns_stream: close(logger) closes stream (the run log's file); otherwise the stream belongs to the caller and is left open.

The tags subsystem and domain (see RunLog) are printed as subsystem[domain] in front of the message; the other key-values follow it as key=value. An exception = err or exception = (err, backtrace) value is printed with showerror on indented continuation lines, as are multi-line values. maxlog = n is honoured per record id, as by the stdlib loggers. Writes are serialised by a lock, so the logger can be shared between tasks.

Aeolus.RunLog.DiagnosticsWriter — Type

The diagnostics time series of a run as CSV (diagnostics.csv of the run folder; diagnostics.nc, with the profiles, is DiagnosticsNCWriter, #337). A nested run: from its NestRunStats, every step, parent_steps, child_substeps, parent_retries, child_retries, substeps_last and max_child_cfl, max_clock_error; on the costly cadence the wall times wall_parent, wall_child, wall_boundary, wall_feedback; from the run's step record (#336) cfl_adv (every row: the largest child-substep CFL since the last row) and wall_step (the windows' wall time); for a two-way run that records its ledger, ledger_<quantity> (the relative conservation error of the last window: each refluxed scalar, momentum_x, mass); and the diagnostics of the two domains under parent. and child.. Use it as the run's sim: collect_diagnostics(run).

The non-equilibrium wall model, per wall it has been initialised on (bottom, top): <wall>.utau_mean (the friction velocity of its active TBLE columns after their last solve, the stress the model applied) and <wall>.kappa_wm (the relaxed dynamic κ of the wall, or the fixed one). Aeolus.RunLog.reduce_diagnostic — Method
reduce_diagnostic(reduction, f::Field) -> Float64

A Diagnostic source that returns a Field is reduced over the field's interior with the KernelAbstractions port's thread-invariant reductions (#336): :max, :min, :maxabs with range_max (exact and NaN-propagating, the bits of a serial maximum), :sum, :mean, :rms with the canonical plane sums (plane_reduce!, ordered_sum), the same bits at any thread count.

Aeolus._constraint_residual — Method
diagnostics(sim::MassWeightedSimulation, sim) -> Vector{Diagnostic}

The sound-proof cores' costly diagnostics: ke (the density-weighted kinetic energy ½∫ρ̄|u|²dV, kinetic_energy), max_abs_u, max_abs_v, max_abs_w, theta_min, theta_max and max_div, the residual of the core's own continuity constraint in s⁻¹: max_anelastic_divergence for the anelastic weighting, max_pseudo_incompressible_divergence for the pseudo-incompressible one (the plain ∇·u is non-zero by design). And the step-record diagnostics of the Boussinesq core (#336) except implicit_iters and cfl_diff_state (the sound-proof cores have no IMEX step; their CFL of the state is the advective one, cfl_adv_state).
